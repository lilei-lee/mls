- **REST API**:6 endpoint(community/property identify + get + 等)。15 条业务单测全 pass。
- 10/10 真实 HTTP 联调全过。

#### 段 3 · claim + 比对引擎 + discrepancy

LA 挂牌时调辞典提交对 property 物理属性的 claim(area_sqm / floor / total_floor / rooms / halls / bathrooms 共 6 字段)。

**比对优先级**(白名单驱动):
1. authoritative_attrs(运营复核确定的权威值)→ 比这个
2. authoritative 不存在 → 比 attribute_claims[] 历史最近一条
3. 都没有 → 不比对(首次 claim 直接接受)

**裁决三分支**:
- 全字段一致 → 直接接受 claim,沉淀到 attribute_claims[]
- 有字段不一致 + force=false → 返 409 + diff 详情(让 MLS 弹窗给 LA 看历史值)
- 有字段不一致 + force=true → 接受 claim(标 unverified)+ 写 discrepancy 工单(每差异字段 1 条)

**discrepancy 4 态**:pending(新生成) / confirmed_new(LA 对) / confirmed_history(历史对) / needs_evidence(等 LA 上传房本凭证)。复核必走,不允许 dismiss。

#### 段 4 · transaction sink

`POST /v1/transactions` —— MLS 在成交 confirmed 时通知辞典:property_code + 成交价 + 成交日 + 双方 agent。辞典记进 `property.transaction_history[]`,不再可改。**这是事实层,只记录,不裁决**。

#### 段 5 · API Key 鉴权 + city_scope + audit_log

- **API Key**:每个外部调用方(MLS 实例 / 第三方)独立 Key,Key 携带 city_scope(允许操作的城市列表)+ permissions + active 标记。
- **city_scope 隔离**:Key 调任何 endpoint 时,如目标 property 的 city_id 不在 Key 的 city_scope 内 → 403。
- **audit_log**:所有写操作(create / update claim / 复核 discrepancy / sink transaction)自动写入 `audit_logs` 集合,字段含 actor_key / endpoint / payload / timestamp / city_id。**未来扩 admin UI 时,所有历史操作都能追溯**。
- V2.1 阶段实际只签 1 个 Key 给 MLS 用,但 schema 全部就位。

#### 段 6 · 数据清空脚本(`5b31d82`)

`scripts/reset_to_v2_1.py`:

- 清空业务数据集合(properties / property_discrepancies / audit_logs / api_keys 业务测试 key 等)
- 保留字典表(cities / districts / 已审核入库的 communities)
- 保留种子 API Key(给 MLS 测试用)
- 幂等执行,反复跑不出错

**用途**:V2.1 上线前,辞典侧一键重置到"空白可用"状态。

### 2.3 段 1-6 关键技术决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 楼盘码格式 | HMAC + base32 + 12 位纯字符 | 不可读防物理细节泄露,12 位空间足够 |
| 城市前缀 | 不加(原 c 选项作废) | "ZJK-..." 与湛江/镇江/舟山等双拼撞 |
| 6 物理字段范围 | area / floor / total_floor / rooms / halls / bathrooms | 客观可测,不涉及主观描述 |
| layout / orientation 归属 | 归 MLS(本档 §五 锁定) | 主观性高,放 claim 比对会污染 discrepancy |
| 比对优先级 | authoritative > 历史最近 > 不比对 | 权威值先,缺时退 historical 兜底 |
| force=true 协议 | LA 看完历史值后明确"确认无误,继续挂" | 二次提交防误操作 |
| discrepancy 不允许 dismiss | 必走运营复核 4 态 | 杜绝"看着不顺手就关了"的 silent corruption |
| transaction sink 不可改 | 写入即终态 | 事实层定义,与 MLS transaction 流程解耦 |
| audit_log 即使无 admin UI 也必做 | 写操作 100% 留痕 | 未来补 UI 时不丢历史 |
| 数据清空策略 | C 选项 — 清业务保字典 | 17 区县 + 已审核小区不重建 |

## 三、辞典 vs MLS 商业模型分离(产品 / 资产)

### 3.1 两个 thing,两条命

| 维度 | 辞典 | MLS |
|---|---|---|
| 性质 | **数字资产**(独占) | **应用产品**(可被复制) |
| 数据 | 永久 / 公共 / 跨品牌共享 | 短周期 / 品牌私有 |
| 客户 | 多个 MLS 实例 / 多家公司 / 多城市 / 第三方 | 一家公司在一个城市的经纪人群体 |
| 价值飞轮 | 越用越富(claim 累积、权威值修正、标准资产沉淀、成交事实) | 用户增长 → 留存 → 续费 |
| 运营归属 | 辞典自有员工(数据治理 / discrepancy 复核 / 标准资产生产 / 权威值修正) | MLS 团队(用户客服 / 房源审核 / 申诉处理) |
| 接入方式 | 对外 HTTP REST + API Key | 一个具体 App + 一个具体后端 |
| 复制成本 | 不可复制(数据本身就是壁垒) | 高度可复制(代码可仿,但用辞典) |
| 生命周期 | 永久(数据不会消失) | 可被替代(MLS 失败,辞典还在) |

### 3.2 实务推论

1. **辞典可以独立部署 / 商业化**——比如未来山西某 MLS 公司想接,签 API Key 即可,不需要 fork 我们的 MLS 代码
2. **MLS 是辞典的一个客户**——心智上是平等的,不是父子
3. **辞典数据治理工作流不归 MLS 端**——磊作为辞典 owner 在辞典 admin 里干活(V2.1 阶段无 UI,走 mongo shell + CLI),不在 MLS 后台干
4. **永远不要在 MLS 后端给辞典数据建副本**——读时调辞典,写时 PUT 给辞典,MLS 自己不缓存(短期 cache 可有,但状态不能 own)

## 四、6 条架构铁律(段 1 commit + Day 21 后续校正)

> 这 6 条是辞典系统的根。**任何后续改造,先确认不违反这 6 条;违反就是动地基**。

### 铁律 1 · 物理隔离

辞典与 MLS 是**两个独立的服务**,不共享 venv / db / 端口 / 进程。

- venv: `property-dictionary/backend/venv/` 与 `mls/backend/venv/` 独立
- db: `property_dict` 与 MLS 业务 db 独立
- 端口: 8001 vs 8000
- 通信: 仅通过 HTTP REST,不允许直接 import / 共享 ORM / 共享数据库连接

**为何**:物理隔离是商业模型分层的代码层映射。任何"嫌麻烦,辞典直接读 MLS 的 listing 集合"的捷径,违反此条。

### 铁律 2 · 数字资产定位

辞典是**独占数字资产**,MLS 是**可被接入的应用产品**。

- 辞典面向多个调用方(MLS 实例 / 第三方系统 / 未来的 web 应用)
- MLS 面向一家公司在一个城市的经纪人

**为何**:这条决定了所有边界——API 设计 / 权限模型 / 运营归属 / 商业模式。

### 铁律 3 · 运营动作归属

- 辞典数据治理(户型标准化 / discrepancy 复核 / 基础数据导入 / 权威值修正 / 标准资产管理)归**辞典自有员工**
- MLS 端运营只管 MLS 业务(用户 / 房源 / 申诉),**不碰辞典数据**
- 未来辞典自带 admin UI(V2.1 不做,走 mongo shell + CLI 替代)

**为何**:工作流分清,不会因 MLS 客服顺手改辞典数据破坏权威值。

### 铁律 4 · 权限分级预留

辞典内三级:**owner / senior / operator**。

- owner:全部权限,V2.1 阶段实际只 1 人(磊本人)
- senior:复核 discrepancy / 修改权威值 / 管理标准资产
- operator:基础数据录入(小区 / 区县 / 城市)+ 受 city_scope 限制

`city_scope` 字段挂在每个 owner / senior / operator 身上,operator 工作范围由 city_scope 限定。所有写操作必经 audit_log。

**V2.1 阶段实施**:schema + 中间件全部就位,实际用户只 1 个 owner,无登录 UI。

**为何**:未来扩团队 0 代码改,加一个 user record 就行。

### 铁律 5 · 多租户预留

每个**外部调用方**(MLS 实例 / 第三方系统)独立 **API Key**。Key 携带:

- `city_scope`:允许操作的城市列表
- `permissions`:可调用的 endpoint 集合
- `active`:启用 / 停用开关

**V2.1 阶段实施**:1 个 Key 给 MLS 用,Key 表 schema 完整,无管理 UI(改库手发)。

**为何**:未来扩张到第二个 MLS 实例(比如保定某公司接入)是改一行 JSON 的事,不是写代码。

### 铁律 6 · 数据归属边界(Day 21 后期校正)

**辞典只持有"物理永久 + 客观可测"的字段**。具体边界:

- **辞典持有的 12 字段**:
  - 6 身份(唯一索引):city_id / district_id / community_id / building / unit / room_no
  - 6 物理可测(claim 工作流):area_sqm / floor / total_floor / rooms / halls / bathrooms
- **辞典还持有**:property_code / authoritative_attrs / attribute_claims[] / standard_assets / transaction_history[] / listing_history[] / 元数据
- **MLS 持有所有其他字段**——包括:
  - 主观描述(layout / orientation —— 每人填法不一致,归 MLS 自由发挥)
  - 营销字段(price_wan / bonus_yuan / sale_points / description / photos / commission_doc_url)
  - 流程字段(status / owner_agent_id / listed_at / sold_at)
  - 全部协作流(showing_requests / showings / transactions / settlements)
  - 全部客户档案(customers)
  - 全部经纪人档案(agents)

**为何**:
- 物理永久 + 客观可测 → 多 LA 挂同一房,辞典裁决到唯一答案
- 主观描述 → 各 LA 自由发挥,放 claim 比对会污染 discrepancy(永远改不完)
- 营销字段 → 完全 listing 周期专属,跨 listing 不共享
- 协作流 / 客户 / agents → MLS 业务流程,跟辞典不打架

**Day 21 中段曾推到极致 "辞典是数据,MLS 只是界面",最终磊收回到 "归到辞典固定的只有城市区域小区楼号单元房号 + 物理可测 6 字段,其他都可变"。本档 §五 数据归属表是这条铁律的字段级落档**。

### 5.3 联动接口(MLS → 辞典)

> Base URL: `http://<dict_ip>:8001/v1/`,所有调用必带 `X-API-Key` Header。

| 场景 | MLS 端动作 | 调用 endpoint | 辞典动作 |
|---|---|---|---|

## 六、辞典 4 层机制(身份 → 识别 → 裁决 → 事实)

### 第 1 层 · 身份(HMAC 算码 + 6 字段唯一索引)

每套房在物理世界有唯一身份(6 字段)。算码模块 `services/coding.py` 用 HMAC-SHA256 把 6 字段 + secret_key 哈希成 12 位 base32 字符串,即 `property_code`。

- 同 6 字段输入 → 同 code 输出(确定性)
- 不同 6 字段输入 → 不同 code(碰撞概率极低)
- 反推不出 6 字段(单向哈希,防物理细节泄露)

**关键**:secret_key 一旦改变,所有历史 code 失效。**生产 secret_key 与开发 secret_key 严格隔离**(`.env` 分文件)。

### 第 2 层 · 识别(命中或创建,幂等)

`POST /properties/identify` 收到 6 字段 → 算 code → 查 properties 表:

- 命中(同 code 已存在)→ 返既有 property
- 未命中 → 建新 property 文档,返新 property

**幂等**:同 6 字段反复调,永远返同一条 property。这是 MLS 端"先调辞典再写本地"双写模式的基石——**不怕重试,不怕并发**。

### 第 3 层 · 裁决(claim + 比对 + 复核 + 权威值)

LA 挂牌时对 6 物理字段提交 claim:

```
POST /properties/{code}/claims
{
  "area_sqm": 100.5,
  "floor": 5,
  "total_floor": 18,
  "rooms": 3,
  "halls": 1,
  "bathrooms": 1,
  "source": {"agent_id": "...", "listing_id": "...", "force": false}
}
```

辞典内部:

1. **比对优先级**:`authoritative_attrs` 优先 → 缺则 `attribute_claims[]` 历史最近 → 都缺则不比对
2. **三分支**:
   - 全字段一致 → 接受 claim,沉淀到 attribute_claims[]
   - 不一致 + force=false → 返 409 + diff `[{field, claimed_value, expected_value, expected_source}]`
   - 不一致 + force=true → 接受 claim(标 unverified)+ 每差异字段写 1 条 discrepancy 工单
3. **discrepancy 4 态**:pending / confirmed_new / confirmed_history / needs_evidence
4. **复核必走**:不允许 dismiss,只能进 4 态之一
5. **权威值更新**:复核 confirmed_new 时,authoritative_attrs[field] 更新为新值;confirmed_history 时,设为历史值
6. **更新触发通知**:authoritative_attrs 变化时,扫所有 listings.property_id == X 且字段值 != authoritative,给每个 LA 推消息 → MLS 端编辑页黄条 + 工作台"待校准"角标

### 第 4 层 · 事实(成交沉淀,只记录不裁决)

`POST /transactions` —— MLS 在 transaction confirmed 时通知辞典:

```json
{
  "property_code": "XXXXXXXXXXXX",
  "price_yuan": 1280000,
  "deal_date": "2026-05-08",
  "ba_agent_id": "...",
  "la_agent_id": "...",
  "transaction_id": "..."
}
```

辞典记进 `property.transaction_history[]`,不再可改。

**事实层是只读累积**——辞典不裁决"这笔成交对不对",MLS 那边的反作弊基石(双方独立填价 + 一致才 confirmed)保证了进入辞典的事实质量。

#### 段 7.6 · transaction sink hook(强制同步 + 5xx 降级 retry)

文件:`mls/backend/transactions.py`

**设计哲学**:
- **强制同步优先**:成交是终点事件,频次极低(一天个位数),200ms 同步开销用户无感,但辞典 transaction_history 永远准 → BA 秒挂同地址第二套时历史值就位
- **5xx 降级保命**:辞典完全挂掉时不阻断 MLS 成交流程(成交是钱)

```python
async def la_confirm(transaction_id):
    # ... 既有反作弊三分支逻辑,达成 confirmed ...
    if status == 'confirmed':
        try:
            # 强制同步 sink(默认路径,99% 走这条)
            await dict_client.sink_transaction(
                property_code=tx.listing_snapshot.property_code,
                price_yuan=tx.la_deal_price_yuan,
                deal_date=tx.la_deal_date,
                ba_id=tx.ba_agent_id,
                la_id=tx.la_agent_id,
                transaction_id=tx._id,
            )
            # 同步成功,直接返
            return tx
        except DictionaryUnavailableError as e:
            # 5xx 重试 1 次仍失败,降级 retry 队列 + 告警
            db['pending_dict_sinks'].insert_one({
                'transaction_id': tx._id,
                'property_code': tx.listing_snapshot.property_code,
                'payload': {...},
                'retry_count': 0,
                'last_error': str(e),
                'created_at': now,
            })
            logger.alert("Dict sink degraded to retry queue", tx_id=tx._id)
            # 不阻断,MLS transaction 仍 confirmed
            return tx
```

后台 retry:APScheduler 每 5min 扫一次 `pending_dict_sinks`,retry_count <= 5,成功即删除该条。

**强一致 vs 一致性损失场景**:
- 99.9% 情况:辞典正常 → 同步成功 → 强一致 ✅
- 0.1% 情况:辞典 5xx → 进 retry 队列 → 短期不一致,但 MLS 端运营可见 alert,人工介入或等 retry 跑通

## 十一、协作约定(承袭 V8.5 + Day 21 新增)

### 11.1 承袭 V8.5

- 代码交付:整替 = Ctrl+A → Delete → Ctrl+V → Ctrl+End → Ctrl+S → q + flutter run(冷启)
- 服务名一致性:前端 service 路径相对(`/listings`)
- FastAPI 路由顺序:具体路径先于 `{id}`
- Pydantic 三处必改:doc / CreateRequest / UpdateRequest
- viewer-aware 格式化器:涉及双方博弈的集合,详情接口必须接 `viewer_id`
- 反作弊比对扩展铁律 / helper 防御性 guard(承袭 V8.5)
- 反作弊脱敏字段 vs 提交标记字段判定铁律(承袭 V8.5)

### 11.2 Day 21 新增

#### 辞典 vs MLS 物理隔离铁律

- 永远不在 MLS 后端 import 辞典任何模块(只 HTTP 调用)
- 永远不在 MLS db 给辞典数据建副本(身份 6 字段冗余例外,且写时反查)
- 辞典服务不可达时,MLS 不能 fallback 用本地副本"假装能用"(数据漂移风险)

#### API Key 管理铁律

- `.env` 必须进 `.gitignore`(辞典侧已就位)
- `mls/backend/.env` 加 `DICT_API_KEY=xxx` 时,必须 push 前肉眼扫
- 生产 Key vs 开发 Key 严格隔离(secret_key 同此规则)

#### 双写双向铁律

- LA 提交 listing → 先调辞典(identify + claim)成功后再写本地 listing
- 辞典调用失败 → MLS 不写本地,返前端"辞典服务暂时不可达"
- transaction sink 是例外:本地 transaction 可独立 confirmed,sink 失败进 retry 队列
- 永远不在"本地写完再调辞典"——这会让漂移成为常态

#### N+1 查询铁律

- BA 看共享库 / 协作详情 / 工作台聚合时,如需补辞典数据,**用 batch endpoint**
- 单条调用只在"打开单个详情页"等场景
