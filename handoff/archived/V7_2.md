## 六、核心业务规则(按模块)

### 6.1 模块一:账号

- 手机号 + 短信验证码登录。注册即自动登录
- 验证码存 fakeredis,有效期 5 分钟,60 秒频率限制
- Token:access 2h,refresh 30d,换取时旧 refresh 拉黑
- 账号状态:active / pending / banned / deleted

### 6.2 模块二:房源

- **一户一码**:MD5(小区+楼号+单元+房号) 前 16 位,同一房源只能一位经纪人录入
- 照片最多 6 张,base64 存 MongoDB(对象存储迁移登账)
- **状态机(当前支持)**:
  - `on_sale` 在售
  - `deposit_paid` 定金已付(Day 7)
  - `transaction_ongoing` 成交进行中(Day 7)
  - `sold` 已成交(Day 7,不可手动,只能由 transaction confirmed 触发)
  - `offline` 已下架
- **流转**:
  - on_sale ↔ deposit_paid ↔ transaction_ongoing → sold
  - 回退:deposit_paid / transaction_ongoing → on_sale(需原因;若有 pending transaction 则拒绝)
  - 下架:只能从 on_sale 走 → offline
  - 重新上架:offline → on_sale
- **V10 其他状态尚未实现**(技术债):coming_soon / paused / pending_check / archived / locked
- 共享库可见:on_sale / deposit_paid / transaction_ongoing / sold(sold 公开展示成交价和日期)
- **带客申请前置**:目前只支持 on_sale 可被申请(V10 规定 deposit_paid 作为 backup 也可申请,本次未改)

### 6.3 模块三:小区库

- MVP 实现 1 个集合 `communities`,3 个接口:search / create / by-id
- 复合唯一索引:`name + district`
- 录入房源时可从小区库选,也可新建

### 6.4 模块四:带客协作

**带客申请(节点 ②③)**:
- BA 填客户姓氏、性别、需求 → LA 审批
- 拒绝理由 5 选 1,还有 other
- 通过后双方身份互通(出手机号,可一键拨号)

**带看确认(节点 ④)**:
- BA 提交:实际带看时间 + 1-3 张现场照片 + 备注
- LA 确认 / 驳回(驳回带理由)
- 只有 confirmed 的带看能进入节点 ⑤

### 6.5 模块五:成交确认(节点 ⑤,Day 7 主题)

**MVP 实现**:

- **前置门槛**:listing 必须处于 `deposit_paid` 或 `transaction_ongoing`
- **发起人**:BA(仅 MVP,LA 回退发起登账)
- **必须关联**:一条 confirmed 的带看记录,且属于发起 BA
- **同一房源单一待确认**:防重复
- **双方独立填价**:BA 发起填价,LA 独立填价(必须分毫不差 + 日期一致)
- **Day 8 视角隔离落地**:LA 在 `pending_la_confirm` 状态下**后端脱敏 + 前端再隐藏**。后端 `_format` 接受 `viewer_id`,LA 视角返回 `ba_deal_price_yuan=None`/`ba_deal_date=None`/`ba_notes=""`。前端读 `viewer_role` 判身份,在 BA 卡片展示"🔒 已提交(防伪隐去)"而非原价格。V10 防伪基石
- **一致 → confirmed**:listing 自动置 sold,成交价 / 日期 / 时间落档。**Day 8 新:同步触发 settlement 自动生成**(如果 listing.bonus_yuan > 0)
- **不一致 → rejected(reject_kind=price_mismatch)**:BA 可修改重提
- **LA 可手动驳回**(reject_kind=manual):带理由
- **BA 可撤回**:仅 pending_la_confirm 状态
- **回退保护**:listing 有 pending_la_confirm 的 transaction 时,不能回退状态到 on_sale
- **成交价单位**:元(整数,分毫不差)
- **UI 防错**:元输入同时显示"约 X.X 万元",提交前二次确认 + 低于 10000 弹警告

### 6.6 模块五下半段:奖金结算(节点 ⑥,🆕 Day 8 主题)

**MVP 实现**:

- **触发**:transaction 变 confirmed 且 listing.bonus_yuan > 0 时,`transactions.la_confirm_transaction` 调用 `settlements.create_settlement_for_transaction` 自动生成
- **金额锁定**:settlement 创建时把 `listing.bonus_yuan` 拷贝进去。**严格意义应该用"BA 提交时"的值,但本 MVP 没在 transaction 里存快照,属近似实现,登债**
- **状态机(线性 3 态)**:
  - `pending_payment` 待 LA 付款(初始态)
  - `pending_receipt` 待 BA 确认已收(LA 已标记已付)
  - `settled` 已结清(终态)
  - `disputed` 异议(占位,MVP 不走流程)
- **本 MVP 仅实现 `pending_payment → pending_receipt`**,即 LA 点"我已付款"这一步
- **BA 确认收款(pending_receipt → settled)**:等 B 对象存储迁完后补,届时同步做"上传转账截图"强制必传
- **查看规则**:仅 LA/BA 双方能查,第三方 403
- **列表合并**:`/pending-my` 后端返 "LA-pending_payment" 或 "BA-pending_receipt",前端按 `viewer_role` 区分卡片动作

**V10 规定但本 MVP 未实现的**(登债):
- BA 确认收款 + 凭证上传(等 B 对象存储)
- 超期提醒(14 天未付/未确认,等推送)
- 异议举报流程
- 奖金历史接口

## 九、坑位档(所有 Day 踩过的坑)

### 坑 1:Pydantic 三处必改
新加字段要同时改:
1. 数据库 doc 结构
2. CreateXxxRequest 模型
3. UpdateXxxRequest 模型(最容易忘)

### 坑 2:Flutter 布局 unbounded height
症状:`RenderFlex children have non-zero flex but incoming height constraints are unbounded.`
修复:最外层用 IntrinsicHeight,或用 mainAxisAlignment: spaceBetween 代替 Spacer

### 坑 3:验证码已过期(注册)
修复:register 直接返 token,跳过二次 login

### 坑 4:AndroidManifest 改完必须全量重建
`q` 退出 flutter run → 重跑 `flutter run`。Shift+R 不行

### 坑 5:url_launcher 拨号失败
Android 11+ 需要 Package Visibility 声明 queries intent

### 坑 6:dio 日志 base64 截断
前端 debugPrint 补打印

### 坑 7:前端 baseUrl 重复前缀
ApiClient 的 baseUrl 已经是 `http://ip:8000/api/v1`,service 里写 `/showings` 而不是 `/api/v1/showings`

### 坑 8:业务文档集合名 ≠ 代码集合名
见 §8 铁律

### 坑 9:FastAPI 路由顺序
具体路径必须注册在 `{id}` 之前。安全顺序:POST /xxx → GET /xxx/list → GET /xxx/specific/{y} → POST /xxx/{id}/action → GET /xxx/{id}

### 坑 10:前端 baseUrl 硬编码 + WiFi 切换
症状:换 WiFi 后 App 连不上,dio connection timeout
修复:改 `lib/config/api_config.dart` 的 baseUrl

**注意冒号全角半角**:必须是英文 `:`,不能是中文 `:`,不然 URL 解析直接崩

### 坑 11:链式 Future 时序 bug
symptom:showing_request_detail_screen 里 transaction 请求永远发不出去
root cause:原代码 `_reload()` 用 `_showingFuture.then()` 延迟 setState 触发 `_transactionFuture`,但 FutureBuilder build 时取的不是同一个 Future 实例
修复:`_transactionFuture` 同步在 setState 里用 `_showingFuture!.then(...)` 链式赋值

2. `GET /transactions/pending-la`

5. `POST /transactions/{id}/la-confirm`

1. `GET /settlements/pending-my`

4. `GET /settlements/{id}`

### 11.4 Pydantic 三处必改口诀

### 11.5 🆕 viewer-aware 格式化器规范(Day 8)

**所有涉及双方博弈的集合,详情接口的格式化器必须接受 `viewer_id`**。transactions 和 settlements 两个 `_format` 都遵循这个规范,返回:

- `viewer_role: "la" | "ba" | null`(前端判身份用)
- 针对 viewer 脱敏的敏感字段(如 pending_la_confirm 下的 BA 填价)
- 不脱敏的字段(名字、时间戳等)正常返

**前端 screen 对应规范**:读 `viewer_role` 判身份,不再用姓名兜底。
