## 三、V2 收官回顾

### 3.1 反作弊基石最终形态(V2.0)

- 双方独立填价 + 独立填日期(天级精度,零容差)
- 任一字段不一致 → 三分支 reject_reason 精准提示
- helper 防御性 guard 兜底,缺字段直接拒
- 视角隔离前后端对称,rejected/cancelled 不漏脱敏
- 1:N 带看场景下"只看最新一条"语义
- manual reject 双重拦截(后端 PATCH 拦 + 前端 BA 红警告 + LA 不渲染修改入口)

### 3.2 反作弊基石设计哲学(完整版)

继承 V8.4 §11.7,Day 20 新增体悟:

1. **场景 5 反作弊基石闭环不是"防止 100% 串通"**:LA + BA 真要串通伪造成交,前置锁 BA 也防不住(他们就是合作的)。系统能做的是:① 双方填价独立 + 一致才通过 ② 留痕完整可审计 ③ 后台巡检 + 事后惩罚。**反作弊基石是"提高门槛 + 留证据",不是"杜绝可能"**

2. **基石的语义完整性 vs 节奏紧迫感的取舍**:Day 20 收官前发现"只比价格不比日期"语义缺口,磊的判断"不做完怎么算收官" — 1.5h 工时换基石完整,这是产品节奏的正确选择。**任何反作弊改造,语义完整性优先于发版节奏**

3. **反作弊比对字段是"白名单驱动"**:future 加比对字段必须从两端推动 — 数据模型 + helper docstring 清单 + reject_reason 分支表 + 前端文案动态读 + spec 同步,任何一处遗漏都是缺口

#### #15 楼盘辞典 — 一房一码 数据模型重构

- **磊原话**:"一套房只要成交过了,就是一套新的房源了,房东变了,我们的楼盘辞典是一房一码这样这套房的历史记录我们都有,这时候是任何经纪人都可以再登房源的"
- **核心概念**:
  - 物理地址 = 永久标识符(community + building + room_no 唯一)→ "房源 code"
  - 一次挂牌 = 一个 listing 文档(短期生命周期:on_sale → sold)
  - 同地址可被反复挂牌(成交后房东变了,任何 LA 都能新挂)
  - 历史成交价、历史协作沉淀在 property code 下,不随 listing 关闭而消失
- **数据模型重构**:
  - 新建 `properties` 集合
    - `property_id` 唯一
    - `community + building + room_no` 唯一索引
    - 历史成交价时间序列(数组)
    - 当前 active listing 引用(0 或 1 条)
    - 历史 listing 引用列表
  - listing 改 `property_id` 引用,property_id 是权威
  - 同 property 同时只能有 1 条 active listing
  - 任何 LA 都能挂(无 LA 锁定)
- **老数据迁移**:现有 listings 反向归集到 properties,历史协作记录(showing_request / showing / transaction)的 property_id 反向填充
- **未拍待板**(实施前必须):
  - 当前 active listing 已挂,新 LA 想挂同 property → 拦截 / 排队 / 通知原 LA?
  - "我的协作记录"在 #13 共享详情页里,是 listing 维度还是 property 维度?
  - BA 看新挂房源,要不要露出"该 property 历史成交价"?
  - 历史挂牌的同地址 listing,LA 是否能看到自己挂过(便于复挂识别)?
  - 房屋号校验加强:同物理地址 100% identification,目前数据库楼栋单元字段是否足够规整?
- **改动面**:后端模型 + 全部用 listing 物理地址的查询改 property_id 引用 + 前端共享库/房源/协作/客户/工作台 + 老数据迁移脚本 + spec 改 5+ 篇
- **关联**:**#5 / #11 / #13 全部需要在本架构上重做**,实施顺序:#15 先,#5/#11/#13 跟
- **工时**:**3-5 天**
- **优先级**:🔴🔴 V2.1 架构主线 #1

#### #11 共享库申请按钮 IA 矫正 — 入口与状态分离

- **磊原话**:"申请过是状态,我曾要带客户看这套房,不能只看一次吧。钮是申请入口,不能具备状态属性,增加个状态"
- **现象**:共享库房源卡片"申请带看"按钮被"申请过"语义锁定,BA 一旦发起过申请,按钮永久禁用,无法对该房源发起任何新申请
- **根因**:按钮承担双重职责 — 既是"操作入口"又是"申请过的状态标记",违反 UI 语义分离原则
- **修法**:
  1. 按钮永远可点(等同于"申请新带看"入口)
  2. "申请过"作为独立状态标签显示在卡片其他位置(如"曾申请 N 次"chip)
  3. 点击按钮 → 跳申请带看页(走 #2 客户选择闭环)
  4. 每次点击 = 一条新 sr
- **连带解决**:
  - V8.4 §六🟡1 "被拒带客申请的再次申请入口"
  - Day 20 反馈第 10 后(双入口 + 立即重提)
- **未拍待板**:同 BA + 同 listing + 同客户重复申请怎么办?(完全相同三元组的 sr 可能产生重复)
- **关联**:#15 楼盘辞典先行后,"曾申请 N 次"是 listing 还是 property 维度? + #13 共享详情页是本条 chip 的合理承载位置

- **优先级**:🔴 V2.1 必修(IA 根本性矫正)

## 十一、Day 20 经验小结(给未来的磊)

1. **8 条真机回归不只是验"已修",还在催生"未发现"** — Day 20 跑 8 条清单的过程中,发现反作弊基石只比价格不比日期(磊判断"不做完怎么算收官"立刻补一刀),发现坑 35 LA 卡 hasSubmitted 不对称,发现 13 条产品反馈。**真机回归是产品反馈的前哨,不能压缩**

2. **"做到我满意再上线"是产品节奏的根本性升级** — 原 V8.4 §5.3 "V2 收官 → 拉种子用户边迭代"是常规 SaaS 节奏,但 MLS 是反作弊基石产品,任何"先放种子再修"都会侵蚀基石信任。Day 20 磊明确取消种子期,V2.1 路线图全部按"完整化"标准推进,这是产品观的成熟

3. **Web 端 Claude 节奏会带歪,被拉回来是好事** — Day 20 中段 Web Claude 发现 LA 卡 hasSubmitted bug 后立刻"找 bug → 立刻修 → 又开新 commit",节奏滚雪球。磊一句"我们有一堆 bug 和设计问题不改,一直在测这些"立刻拉回 V2 收官主线。**Web Claude 应固守 V8.4 §5.1 铁律 — 任一卡住先回写本会话不贸然修,登债不当场补**

4. **Claude Code 跑测试的边界要明确** — 凡能 API/db 注入跑的回归(R2-a/b/c + R2 验 5 + R3 manual reject)Claude Code 全包,凡纯前端 UI(验 7/8 工作台角标 + 待办出现)磊真机扫。这种 "API-level + UI-level 分工" 让 V2 收官的回归从估时 30-45min 实际跑了 ~60min,但保真度更高

5. **取证脚本和工单写法的进步** — Day 20 让 Claude Code 跑双视角 token + curl 取证(LA 卡 hasSubmitted 调查),工单格式"列上下文 + 不改代码"几次下来很顺。**未来涉及"先取证,再决策修不修"的 bug,这套工单模式可复用**

6. **登债的拆分艺术** — 13 条产品反馈拆 15 条登债,关键是识别"同一现象但根因不同 → 不同条目"(如反馈 5 + 反馈 11 共同指向 #5 架构改造,反馈 11 + 反馈 13 共同指向 #15 楼盘辞典)。**登债不是 1:1 抄反馈,是先理解产品意图,再按改造单元归类**

7. **架构主线 #15 楼盘辞典是 MLS 的产品观分水岭** — 在此之前 MLS 把 "listing" 当成 first-class entity,在此之后 "property" 才是 first-class,listing 只是"挂牌行为"。这跟二手房交易现实(房子永久存在,挂牌反复发生)对齐,是数据模型对业务真相的妥协。**V2.1 阶段 #15 不做完,后面所有 IA 改造都建在错的根上**
