## 九、🔑 坑位档(累计到 Day 16)

V8.1 已记坑 1-27。**Day 16 新增坑 28-31**:

### 🆕 坑 28(Day 16):新接口返回结构嵌套,前端抄旁边方法的脑型崩

`/showings/direct` 返 `{success: true, data: {showing_id: ...}}`(嵌套),前端 `showing_service.createDirect` 抄 `submit()` 的 `resp.data['showing_id']`(扁平)导致 `Null is not a subtype of String` 崩。**经验**:每写新 service 方法前,先 Swagger 试一次接口,看清返回结构再写解析,不能抄旁边方法的脑型。

### 🆕 坑 29(Day 16):跨模块新写 doc 时字段集对照不全

`customers.py:create_direct_showing` 写新 showing 时,字段集没对齐 `showings.py:submit_showing` 的全集,漏 `ba_submitted_at` / `ba_agent_name` 等,导致 `_format_showing` 在 LA 拉详情时 `KeyError` 500。**经验**:跨模块新写 doc 前,先用 `db['集合'].find_one({}, sort=[('created_at',-1)])` 拉一条已有的对照字段全集,再起手写新 insert_one;formatter 一律 `.get()` 容错。

### 🆕 坑 30(Day 16):状态码命名前缀风格不统一,字典 key 抄错难发现

带看是 `pending_confirm`(无 la 前缀),成交是 `pending_la_confirm`(有 la 前缀),都是"等 LA 处理"。`StatusLabels._showing` 字典首条 key 一开始就把成交那边的 key 抄过来了,因颜色映射对了所以历史上一直没暴露,Day 16 直接带看撞上才发现。**经验**:写状态码字典时,别脑补 key,用 `db.集合.distinct('status')` 列出真实存在的所有 key 再一一映射。

### 🆕 坑 31(Day 16):整替整文件后必须冷启,大写 R 不刷新 widget tree 结构

整替 `showing_request_create_screen.dart` 加客户来源区块后,真机大写 R 热重启没刷新到新结构,表现是"按钮位置看起来没变"。**经验**:**整替整文件 = 一定 q + flutter run**,涉及新加方法 / 新加成员变量 / 新引入子组件时尤其。`r`(小写)只刷 build,`R`(大写)只刷 widget,只有冷启会重建 dart isolate。

**经验 5:脱敏函数的触发条件按"业务保密区间"设计,不按"业务流程瞬间"设计**

bug 表现:_format 的 mask_ba 写成 `is_la and status == "pending_la_confirm"`,

防范规则:写脱敏 / 权限判断时,先想清楚"业务保密的区间是什么",
再翻译成 status 集合,不要顺手抓最近触发的那一个状态。

理解成"防 LA 抄 BA"单向问题。但 BA 同样能从 LA 价格倒推 LA 的客户、
真实成交价、佣金结构,反向作弊也成立。任何"双方独立填报后比对"机制,
mask 必须对称双向。

防范规则:凡涉及"双方独立 / 双盲"逻辑,grep 检查代码里 mask_X / hide_X /
filter_X 之类函数,看 X 是否成对出现。一个方向有一个方向没,99% 是漏。

### 经验 8
