## 十、Day 17 经验总结（10 条）

| # | 经验 | 防范规则 |
|---|---|---|
| **1** | Windows GBK 控制台是暗坑 | 迁移脚本顶部加 `sys.stdout.reconfigure(encoding='utf-8')`；脚本不用 emoji |
| **2** | apply 中途崩 → 先观测 | MongoDB 无事务回滚。print 崩不代表写入没成功。第一动作跑校验，不是修代码重试 |
| **3** | 协作铁律 4（已落 CLAUDE.md V1.2 铁律 7） | 只读探查命令的输出必须用户亲眼看过才进入下一步 |
| **4** | 多入口写同一集合时改一处必须 grep 全部入口对齐字段集 | `grep -rn "<collection>.insert"` 必查所有入口 |
| **5** | 脱敏函数触发条件按"业务保密区间"设计，不按"业务流程瞬间"设计 | mask 条件用 status 集合（`!= "confirmed"`）而非单一状态 |
| **6** | mask 逻辑必须双向 | 反作弊 = 双方互相不可见，grep 检查 mask_X / hide_X 是否成对出现 |
| **7** | UI 异常先 curl 直打接口证伪 | 看到"应该过滤的没过滤"先 curl 验证后端是否真返脏数据，再决定改前端 / 后端 |
| **8** | 数据一致性的根因往往不在显示而在多源不同步 | 用 [前端显示 / 接口返回 / DB count] 三方对照模板 |
| **9** | Pydantic 校验是后端数据卫生第一道闸 | 用户可编辑字段全部加 validator（数值范围 / 长度 / 枚举） |
| **10** | 历史回归测试要测"修复对老数据是否有效" | 任何字段集变更 / 写入逻辑变更必须配套写回填脚本 |

**经验 4 + 经验 10 是同型问题两个方向**：
- 经验 4：横向同步（各入口字段集对齐）
- 经验 10：纵向同步（新写入逻辑要回填老数据）

### 关键决策

**1. 归并键场景化：回填用强键，去重用弱键**
- 历史回填：4 字段强键 `(BA, surname, gender, listing_id)`
- 日常 UI 去重：3 字段弱键 `(BA, surname, gender)` + BA 人工确认

理由：本库实际存在 2 对"同 BA + 同姓 + 同性别 + 不同房源"的不同客户。3 字段弱键静默合并 = 数据灾难。

**2. "只建不并"原则**
回填脚本不跨组查 customers 集合做属性匹配。组内有 customer_id 复用，无则新建。跨组归并留给 BA 在 UI 手动。

**3. 与 Day 15 的关系**
Day 15 (migrate_collab_1n.py) 只做 1:N 重复申请合并，不碰 customer_id。本任务补的是 Day 15 未覆盖的字段缺失。

1. 排查与上一次相关迁移的关系（漏迁 / 新缺口 / 业务跳过？）
2. 归并键场景化（回填强键，去重弱键 + 人工）

### 任务颗粒度匹配 Qwen 能力（Day 17 经验）

| 任务类型 | 颗粒度 | 给 Qwen 的方式 | 说明 |
|---|---|---|---|
| 整块测试任务 | **大颗粒** | 整块需求 + 输出格式约束发过去，Qwen 自跑 | 数据一致性 / 健壮性 / 历史回归 — 跑得很好 |
| 多步代码重构 | **小颗粒 + 强制 PLAN** | 必须先 PLAN 等磊回 ok | 路由 reorder 出脏现场就是没 PLAN |
| 单文件单点修改 | **完整 diff 给 Qwen apply** | Web 端 Claude 写好 str_replace 的 old_str/new_str | _StatusBadge 补 case 这种 5 分钟搞定 |
| 写库脚本 | **强制 dry-run + apply 分离** | 铁律 1 + 8 + 9 + 10 全部生效 | 数据卫生不能马虎 |
| 诊断查询 | **一条只读命令一次贴原文** | 铁律 9 强制贴原文 | 摘要失真害死人 |
| 写代码（dart 组件等） | **给清晰需求让 Qwen 写** | Web 端 Claude 不替它写代码 | 工程师角色不替执行手干活 |

### Qwen 暴露的常见问题（Day 17 实测）

1. **协作铁律 7 反复违反**：跑了只读命令不贴输出就深挖（4+ 次）→ 加铁律 9 治理
2. **复制粘贴语法错误**：重写脚本时 if/else 重复块、孤儿 print（2 次）→ 加铁律 10
3. **多步操作不规划**：路由 reorder 时先加新的不删旧的，造成脏现场（1 次）→ 加铁律 8
4. **偷懒只贴摘要不贴原文**：必须反复要求"贴完整原文"（4+ 次）→ 铁律 9
5. **任务范围漂移**：让做 A 顺手做 A+B（按钮文案那次）→ 加铁律 11

#### Day 18 真新经验(值得记入 V8.4 经验库)

**教训 1:路由 typo 不一定表现为 404,可能是"莫名崩溃"**

- 早上的 `/listings/new` typo → 404 友好提示(易诊断)
- 下午的 `/showing-request/received` typo → 详情页加载崩溃(`type Null is not a subtype of Map<String,dynamic>`),AppBar 标题显示"带客申请详情"
- 根因:typo 形态命中了动态参数路由 `/showing-request/:id`,字符串字面量 "received" 被当作 id 传给 detail_screen,detail_screen 调 `/api/v1/showings/by-request/received` 后端返 400 + "无效的申请ID",前端 unwrap 崩溃
- 防范:看到表现为"详情页崩溃但接口报 invalid id"时,**第一反应是上游路由 typo,不是详情页 bug**

**教训 2:诊断陷入死循环时,先看 dio log 的真实 URL**

- 今天我们在前端代码里绕了 1+ 小时找 `as Map<String, dynamic>` 强转的崩溃源
- 真凶证据在 dio log 第一条:`/api/v1/showings/by-request/received` 这个奇怪的 URL 字面量
- 教训:UI 崩溃 + 错误信息泛化(像 type cast 这种通用错误)时,**先看 dio log 的真实接口调用 URL**,不要只看代码强转
- 是 V8.3 经验 7(UI 异常先 curl 直打)的延伸:经验 7 是"已知接口路径时 curl 验证",这条是"未知接口异常时先看 dio log 找真实路径"
