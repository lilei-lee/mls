## 一、战略定位（不变）

- **平台定位：** 张家口二手房经纪人之间的房源共享与联卖协作系统。纯B端基础设施，不面向购房客户。
- **与内容业务的关系：** 完全独立。MLS是磊的公司独立业务线，与老谢等主播的内容业务互不关联。
- **与贝壳的区别：** 贝壳是C端流量平台，经纪人是平台的打工人。MLS是B端协作网络，经纪人保持独立，平台为经纪人服务。平台不抽佣，赚基础设施使用费。
- **目标市场：** 贝壳占约50%市场，剩下50%的非贝壳系小门店和独立经纪人是目标用户。
- **市场时机：** 市场低迷期，中介费低，经纪人单打独斗效率极低，联卖能显著提升匹配效率和成交速度。

## 二、核心机制（不变）

### 2.1 单边代理
每个经纪人只代表一方利益。Listing Agent代表卖方，Buyer's Agent代表买方。各自向各自的委托方收取服务费，费用标准由经纪人与委托方自行约定。**单边代理是每条交易维度的角色分配，不是经纪人身份的限制。同一经纪人可以是A房源的Listing Agent同时是B房源的Buyer's Agent。同一房源中LA=BA时走自促成交流程（详见模块五§3.5）。**

### 2.2 独家委托
房源录入MLS原则上要求独家委托。种子期不强制，通过后台开关控制强制程度。独家协议优先于先到先得规则。「即将上市」状态强制要求独家委托协议，此规则不可关闭。

### 2.3 联卖与合作奖金
房源录入共享库后，网络内所有经纪人都可看到并发起带客申请。房源方可设定合作奖金激励更多经纪人带客。**奖金本质是Listing Agent从自己的中介费收入中拿出的一部分，用于激励促成成交的Buyer's Agent。中介费由房东支付给LA，奖金由LA自愿设定和分配，平台不介入资金流向。**

### 2.4 收费模式
- **经纪人向委托方收费：** 各自向各自的委托方收取服务费，平台不介入。
- **平台收费：** 前期免费，后期以年费/会员费形式收取基础设施使用费。平台不从交易中抽佣。

### 2.5 匿名带客机制
带客申请审批前，双方互不知道对方身份。Listing Agent审批时只能看到客户姓氏、性别、购房需求描述。审批通过后双方身份互相公开。

### 2.6 平台留痕而非信息隔离
一键拨号直接拨出对方真实电话，不使用虚拟号中转。所有联络动作由平台记录时间和参与方。电话号码不在页面上以文字形式展示，经纪人需通过点击按钮拨号——点击动作本身就是留痕节点。

### 2.7 不做客户归属
同一个购房客户可以被不同的Buyer's Agent带去看同一套房。平台不做客户归属判定。

### 2.8 不设信用积分
通过交易留痕数据本身来体现经纪人的行为记录，不压缩为一个分数。

### 2.9 门店老板同时具备经纪人身份
门店老板注册门店账号后，同时具备完整的经纪人身份。可以直接参与全部业务。门店管理功能是附加层，不赋予任何业务特权。

## 四、房源状态体系（不变）

| 状态 | 含义 | DOM计算 | 备注 |
| --- | --- | --- | --- |
| 即将上市 | 已签独家委托但未准备好看房 | 不计算 | 强制独家委托，最长30天。到期立即下架，不再给即将上市选项 |
| 在售 | 正常展示，可被申请带客 | 正常计算 | 唯一触发「待确认」的状态 |
| 定金已付 | 买家已付定金，仍可能反悔 | 正常计算 | 仍可申请带客（backup）。必须上传定金凭证 |
| 成交进行中 | 正在走过户流程 | 暂停计算 | 可回退到在售。委托到期只提醒不下架 |
| 已售 | 通过平台成交确认 | 停止 | 只能通过留痕节点⑤触发 |
| 撤牌 | 其他渠道成交/房东不卖/暂停超60天自动转入 | 停止 | 需选原因，不展示。可从撤牌恢复上架转在售 |
| 暂停挂牌 | 经纪人主动暂停 | 暂停计算 | 超过60天自动转撤牌 |
| 待确认 | 7天未更新（内容或状态确认） | 正常计算 | 仅作用于「在售」状态 |
| 已下架 | 14天未更新/委托到期/即将上市到期 | 停止 | 仅从「待确认」触发（委托到期和即将上市到期除外） |
| 锁定 | 经纪人离职，房源待移交 | 暂停计算 | 共享库展示但不接受带客，移交后恢复原状态 |

### DOM计算方式
DOM = 在售总天数（扣除暂停挂牌/锁定/成交进行中的时间）。参考美国MLS的Active DOM机制。数据结构：dom_paused_at（暂停时间）+ dom_accumulated（暂停前累计天数）。每次进入暂停类状态时将已计算天数加入dom_accumulated，恢复时从dom_accumulated继续累加。

三层推送架构，最大化到达率+兜底可靠性：

```
┌─────────────────────────────────────────────────────┐
│  第一层：离线推送（核心通道）                        │
│  极光推送 JPush 聚合：                              │
│   ├─ 华为 HMS Push                                  │
│   ├─ 小米 MiPush                                    │
│   ├─ OPPO Push                                      │
│   ├─ VIVO Push                                      │
│   ├─ 荣耀 Push                                      │
│   ├─ 魅族 Flyme Push                                │
│   ├─ FCM（Google服务，海外备用）                    │
│   └─ APNs（iOS预留）                                │
│  → 覆盖App在后台/杀死状态下的到达                    │
└─────────────────────────────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────────┐
│  第二层：可选辅助通道（微信服务号）                   │
│  用于补充场景：                                      │
│   ├─ 关键事件（带客申请/成交确认/争议）双通道冗余    │
│   ├─ 经纪人未安装App/卸载App时的兜底                │
│  前提：经纪人已关注服务号且完成UnionID绑定           │
│  → 覆盖App不可达时的重要通知                         │
└─────────────────────────────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────────┐
│  第三层：App内消息中心（兜底）                       │
│  所有通知无论是否推送成功，都写入notifications集合    │
│  App启动时拉取未读+红点/徽标展示                     │
│  → 保证任何通知在打开App后都能看到                   │
└─────────────────────────────────────────────────────┘
```

**渠道选择规则**：
- **高优先级**（必须触达）：极光推送 + 服务号 + 消息中心（三通道冗余）
- **中优先级**（当天了解）：极光推送 + 消息中心
- **低优先级**（应用内即可）：仅消息中心

**到达率监控**：所有推送结果记录到 push_log，后台大盘监控各通道到达率，低于阈值自动告警。

### 6.6 身份认证架构（V10 App版新）

```
┌─────────────────────────────────────────────────────┐
│  身份主键：手机号（phone_number，UNIQUE）            │
│  绑定标识：                                          │
│   ├─ 微信UnionID（可选绑定，用于服务号推送+快捷登录） │
│   ├─ 极光Registration ID（设备推送token）            │
│   └─ 设备指纹（设备信任）                             │
└─────────────────────────────────────────────────────┘
```

**登录方式**：
1. **主路径**：手机号 + 短信验证码（首次注册和日常登录）
2. **辅助路径**：微信开放平台登录（已绑定手机号的账号快捷登录，通过UnionID查询账号）
3. **二次快捷**：生物识别（首次登录后启用，指纹/面部识别）
4. **密码**（可选）：经纪人可选设置密码作为验证码备用登录

**会话管理**：
- JWT Access Token（2小时）+ Refresh Token（30天）
- 多设备登录：最多3台设备同时在线，第4台登录踢掉最早的
- 异地登录二次验证（省份变化时要求重新短信验证码）

## 十、关键设计决策记录（V9业务决策全量保留）

> 以下业务决策与小程序版本完全一致，App版不做任何业务变更。

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 信用积分系统 | 砍掉 | 美国MLS不设积分；交易留痕数据本身就是最好的信用记录 |
| 电话显示方式 | 一键拨号（真实号码） | 让拨号动作成为留痕节点 |
| 客户归属 | 不做 | 共享平台比拼服务，不是圈地 |
| 匿名带客 | 审批前双方不知身份 | 防止人际关系干扰业务判断 |
| 即将上市状态 | 强制独家委托 | 没有协议不允许占坑 |
| 已售状态 | 只能通过成交确认流程触发 | 保证成交数据100%真实 |
| 罚款 | 不做 | 无收费渠道执行不了 |
| 虚拟号中转 | 不做 | 留痕目的是记录动作不是隐藏信息 |
| 带客申请7天有效期 | 通过后7天未提交带看记录自动失效，过期后需重新申请。第5天提醒，第7天过期通知双方 | 防止僵尸申请堆积，重新申请成本低 |
| 门店老板身份 | 同时具备经纪人身份 | 管理是附加层不是替代 |
| 处罚体系统一 | 模块五为唯一标准 | 避免两套处罚体系矛盾 |
| 暂停时房源处理 | 保留但标注，不下架 | 直接下架伤害无辜房东 |
| 联卖开关前置 | 审核通过前强制关闭 | 避免无人审批的带客申请 |
| 暂停挂牌状态 | 新增，区别于撤牌 | 暂停是暂时，撤牌是终结 |
| 成交进行中DOM | 暂停计算 | DOM继续增加误导市场 |
| 成交进行中回退 | 允许回退到在售 | 过户阶段交易可能取消 |
| 委托到期处理 | 14天+3天两次提醒 + 7天宽限期 | 不让经纪人措手不及 |
| 关注小区 | 新增功能 | 第一时间获知目标小区新房源和降价 |
| 小区成交数据 | 新增页面 | CMA数据是MLS最核心的数据资产 |
| 批量审批 | 支持批量同意和批量拒绝 | 热门房源需要高效处理 |
| 数据导出频率 | 经纪人3次/天，门店5次/天，后台不限 | 防止数据被批量抓取 |
| 归属变更不受状态限制 | 独家委托效力高于一切展示状态，但不高于交易状态 | 在售/暂停/待确认允许变更；定金已付/成交进行中/已售锁定归属 |
| 归属变更时奖金重置 | 奖金重置为0，新归属人自行设定 | 奖金是经纪人自己出的钱，换人后新人没有义务替前任承担 |
| 归属变更时关联数据处理 | 待审批转移、已通过保留并通知、已完成带看不动 | 申请人不需要重新提交，但需知道Listing Agent换人了 |
| 待确认作用范围 | 仅作用于「在售」状态 | 定金已付/成交进行中/暂停挂牌等状态不触发待确认 |
| 暂停挂牌取消开放日 | 自动取消未来开放看房日并通知 | 避免经纪人按通知上门却发现房源暂停 |
| 经纪人离职房源处理 | 房源锁定，门店老板重新分配 | 保护房东利益，确保房源有人负责 |
| 踢出时未结算奖金 | 标记「需人工介入」，后台主动跟进 | 不因极端处罚导致合作方损失奖金 |
| App首页 | 工作台仪表盘，非房源列表 | 让经纪人第一眼看到该做什么 |
| 合作评价可见性 | 预留功能，后期平台成熟后开放 | 避免早期样本量不足导致评价不公 |
| 恢复在售通知拆分 | 区分「从暂停恢复」和「从成交回退」 | 两种原因对经纪人决策意义完全不同 |
| 反向匹配（收藏热度） | Listing Agent可见房源被收藏次数 | 帮助判断市场关注度，不暴露收藏人身份 |
| 自动匹配推送（订阅搜索） | 预留功能，后期开放 | 种子期房源少无价值，房源上千后再做 |
| 奖金可自由调整+下调通知 | 设定后可上调或下调，下调时强制通知所有已有带看记录的BA和收藏者 | 鼓励LA设置奖金，下调有通知义务保护BA知情权 |
| 成交确认只关联一条带客记录 | 不存在分奖金 | 奖金只付给促成成交的那一位Buyer's Agent |
| 成交后通知未关联的Buyer's Agent | 有带看记录但未被关联的经纪人收到成交通知 | 保障维权时效，90天内可举报 |
| 被举报方暂停期间答辩期顺延 | 答辩期延至暂停解除后7天 | 暂停无法登录不应剥夺答辩权 |
| 门店老板处罚双维度 | 处罚只针对个人经纪人身份，门店保留不关闭 | 不因个人违规牵连门店其他经纪人 |
| 成交进行中不触发委托到期下架 | 只提醒续委托，不自动下架 | 交易正在走最后流程，下架会中断交易 |
| 归属变更时开放日取消 | 自动取消未来开放看房日，新归属人需重新设定 | 开放日是原经纪人安排的，换人后需重新协调 |
| 归属变更时个人备注不迁移 | 原经纪人保留只读，新归属人从零填写 | 个人备注是私人笔记，不应交给他人 |
| 归属变更申诉机制 | 先执行后申诉，申诉成功则回滚 | 后台已审核独家委托，申诉成功率极低，不值得冻结7天 |
| 归属变更待审批申请标注来源 | 转移给新Listing Agent的申请标注原Listing Agent姓名 | 帮助新人理解上下文做审批判断 |
| 锁定房源接受独家委托变更 | 独家委托始终最高优先级，高于门店内移交 | 独家委托是法律效力凭证，门店移交是内部管理行为 |
| 归属变更全面通知 | 奖金重置通知收藏者+所有相关Buyer's Agent | 所有利益相关方都需要知道Listing Agent换人了 |
| 锁定状态是正式房源状态 | 在状态流转表、展示规则、DOM计算中均列出 | 跨模块一致性审查补全 |
| 锁定期间待审批申请冻结 | 冻结等待移交，移交后转给新Listing Agent | 锁定期间没有人能审批，冻结比自动拒绝更合理 |
| 锁定状态DOM暂停计算 | 与暂停挂牌一致 | 房源展示但不接受带客，DOM继续增加会误导市场 |
| 成交通知未关联Buyer's Agent | 成交完成后通知所有曾带看但未被关联的BA，提示90天举报时效 | 保障维权知情权 |
| 暂停挂牌通知已通过带客方 | 已通过但未完成带看的BA收到暂停通知（独立于收藏通知） | BA通过申请通道建立关系，不依赖收藏行为 |
| 关闭带客申请通知Listing Agent | BA关闭申请后通知LA | LA可能在等BA带客，知道对方放弃了可以调整预期 |
| 门店老板收到名下经纪人处罚通知 | 四个等级全部通知门店老板 | 处罚影响门店房源和业务，门店老板需要知情 |
| 自动下架后经纪人自行恢复 | 后台不提供恢复操作，经纪人在App内自行更新信息恢复上架 | 自动下架是因为经纪人未更新，恢复责任在经纪人 |
| 即将上市到期立即下架 | 到期不操作立即下架，之后不再给「即将上市」选项 | 即将上市是占坑机制 |
| 暂停挂牌60天自动转撤牌 | 60天到期自动转撤牌，经纪人自行操作恢复上架 | 比软提醒更干脆 |
| 委托到期+成交进行中不下架 | 只提醒续委托不自动下架 | 交易进行中下架会中断交易 |
| 「更新」的定义 | 内容更新（修改房源信息）+ 状态确认（确认继续上架） | 核心目的是防止已售未下架的僵尸房源 |
| 定金已付必须上传凭证 | 标记定金已付时必须上传定金凭证，虚假标记属严重违规 | 防止利用定金标记阻止归属变更 |
| 归属变更竞态条件防护 | 申请时锁定状态快照，执行前二次校验 | 解决审核窗口期的竞态条件 |
| 新归属人不承担旧奖金承诺 | 归属变更后旧奖金承诺对新归属人无约束力 | 奖金是个人承诺，换人即重置 |
| 成交确认双轨制 | 有BA的由BA发起LA确认，无BA的自促成交走完整带看流程 | BA最清楚自己带的客户 |
| 暂停/踢出交易处理 | 暂停：进行中事务冻结等解除。踢出：门店经纪人转门店老板代处理 | 交易不因处罚中断 |
| 门店老板账号切换角色 | 一个账号登录后可切换「门店管理」和「个人经纪人」两个入口 | 彻底隔离处罚影响 |
| 任何状态变更取消开放日 | 所有房源状态变更都取消未来开放日 | 统一规则 |
| 开放日签到经纪人互不可见 | 签到列表仅Listing Agent可见 | 匿名机制在开放日同样生效 |
| 收藏计数原子操作 | houses.favorite_count使用数据库原子操作更新 | 防止并发收藏导致计数不准确 |
| DOM采用美国MLS方式 | DOM = 在售总天数，扣除暂停/锁定/成交进行中时间 | Active DOM更准确反映市场表现 |
| 成交确认BA催促与LA回退 | BA发起为主，7天未发起LA催促，14天LA可备选发起 | 防止BA忘记发起 |
| 成交确认LA响应时限 | LA收到后7天内必须确认或驳回，超时自动生效 | 防止LA拖延 |
| 同一房源单一待确认成交 | 同一房源只能有一个待确认的成交记录 | 防止并发混乱 |
| 自动撤牌时带客申请冻结 | 暂停超时自动转撤牌时，带客申请冻结不关闭 | 保护BA权益 |
| 撤牌期间委托到期 | 恢复上架时系统检查委托状态 | 防止过期委托恢复上架 |
| 门店老板被踢出管理权保留 | 四级踢出只禁用经纪人入口，门店管理权永久保留 | 门店管理是财产权不是业务权限 |
| 定金凭证先标记后巡检 | 上传凭证后立即标记生效，后台巡检虚假凭证则回滚+严重违规 | 与"先执行后申诉"原则一致 |
| 定金回退异常监控 | 30天内反复标记/回退超过2次触发异常审查 | 防止反复锁状态 |
| 暂停/踢出卡住成交确认的后台代确认 | 任何一方被暂停/踢出，另一方可申请后台代为确认 | 交易不因处罚中断 |
| 举报时效从双方确认后起算 | 90天从成交确认双方通过后开始计算 | 防止LA拖延消耗举报时效 |
| 房源唯一索引→楼盘字典 | 一户一码终身不变 | 楼盘字典是MLS最核心的数据资产 |
| favorite_count定期校准 | 每日凌晨用favorites集合count覆盖 | 保证计数最终一致性 |
| 暂停期间可登录操作进行中交易 | 暂停经纪人可登录，仅操作进行中的成交确认/奖金结算/带看确认/争议答辩 | 防止暂停卡死合法交易 |
| 成交价双方独立填写 | BA填成交价，LA确认时独立填成交价，一致才通过 | 任何一方都无法单独篡改 |

| 自促成交走完整流程 | LA以LA+BA双重身份走完整带看流程 | 消灭"无带看记录的成交"分支 |

| LA暂停时待审批申请冻结 | LA被暂停时，待审批的带客申请标记为"审批暂停"，通知BA | 参照锁定状态处理逻辑 |

| 暂停期间归属变更优先于冻结 | LA暂停期间发生归属变更时，冻结的申请按归属变更规则转移 | 归属变更优先级高于暂停冻结 |
| 开放看房日定位Broker Open House | 开放日是经纪人集中踩点评估，不带客户 | B2B平台定位一致 |
| 驳回超限冻结只阻止发起不阻止确认 | 冻结只阻止BA发起成交确认，不阻止在LA回退发起场景中作为确认方 | 冻结精确到"发起"动作 |
| 合作奖金来源表述修正 | 奖金是LA从自己中介费中拿出的一部分激励BA | 消除"房东承担"歧义 |
| 无定金交易直接签约路径 | LA标记"无定金直接签约"并上传购房合同照片 | 覆盖张家口市场中不走定金的真实交易场景 |
| 奖金锁定时点=BA提交成交确认时 | 结算单金额取BA提交成交确认时刻的奖金值 | 消除锁定时点歧义 |
| 7天有效期=提交带看记录 | 通过后7天内BA需提交带看记录 | 7天是BA行动窗口，不是整个流程时限 |
| 7天有效期归属变更重置 | 归属变更时转移的已通过申请，7天从转移时刻重新计算 | 换LA等于新合作起点 |
| 奖金调整通知=已通过BA+收藏者 | 通知已通过的BA+收藏者，待审批BA不通知 | 精确到已建立合作关系的BA |
| 无定金路径纳入异常监控 | 30天内标记定金/无定金直接签约/回退合计超2次触发审查 | 防止绕过异常监控 |
| 自促成交受7天有效期约束 | 自动通过审批后7天内需提交带看记录 | 规则统一无豁免 |

## 十二、App端技术决策详细说明

### 12.1 手机号+验证码登录流程

```
用户打开App
  ↓
启动页 → 版本检查 → 隐私政策同意（首次）
  ↓
登录页
  ↓
[手机号输入] → [获取验证码] → [短信到达] → [输入验证码]
  ↓
后端校验
  ├─ 新用户 → 进入注册信息填写页（姓名/身份证/所属门店等）
  └─ 老用户 → 检查设备信任 → 工作台
          ├─ 已信任设备 → 直接登录
          └─ 新设备/异地 → 二次验证（邮箱或安全问题或人工审核）
```

**验证码规则**：
- 6位数字，有效期5分钟
- 60秒内不可重复获取
- 同一手机号每日最多10条
- 单IP每日最多50条
- 连续3次错误锁定手机号15分钟

### 12.2 微信开放平台登录（辅助路径）

前提：用户已完成首次手机号注册并在"账户设置"中绑定微信。

```
用户点击"微信登录"
  ↓
fluwx 唤起微信授权
  ↓
获取 code → 后端换取 access_token + UnionID
  ↓
查询 wechat_bindings 集合
  ├─ UnionID已绑定 → 直接登录对应账号
  └─ UnionID未绑定 → 提示"请先用手机号登录后绑定微信"
```

### 12.3 生物识别流程

首次使用条件：账号已通过手机号登录至少一次。

```
用户在"账户安全"中启用生物识别
  ↓
local_auth.authenticate → 设备弹出指纹/面部识别
  ↓
成功后在 flutter_secure_storage 存储加密的refresh_token
  ↓
下次打开App → 启动页指纹识别 → 用存储的refresh_token续期access_token → 工作台
```

**安全边界**：
- 连续3次识别失败，禁用生物识别24小时，强制手机号验证码登录
- 账号更换手机后自动禁用生物识别（用户需重新启用）
- 卸载App自动清除生物识别凭据

### 12.4 推送通道优先级与去重

```
后端事件触发推送
  ↓
通道调度器判断事件优先级+用户设置
  ↓
  ├─ 高优先级事件 → 极光推送 + 微信服务号（如已绑定+用户未关闭） + App内消息中心
  ├─ 中优先级事件 → 极光推送 + App内消息中心
  └─ 低优先级事件 → App内消息中心
  ↓
每条推送生成唯一 message_id
  ↓
App收到推送时检查本地已显示消息ID池
  ├─ 已显示过 → 丢弃（去重）
  └─ 未显示过 → 显示通知 + 写入本地池 + 标记 push_log.delivered
```

### 12.5 离线策略

| **场景** | **处理** |
|---|---|
| 工作台数据 | 本地Hive缓存最近一次拉取的数据，离线时展示缓存+"离线模式"标签 |
| 我的房源列表 | 本地缓存自己的房源，离线可查看但不可编辑 |
| 共享房源库浏览 | 离线展示缓存的搜索结果，无法发起新搜索 |
| 消息中心 | 本地缓存最近30天消息，离线可查看 |
| 带客申请审批 | 必须在线（防止基于过期数据审批） |
| 房源编辑/录入 | 必须在线 |
| 成交确认/奖金结算 | 必须在线 |
| 上传照片 | 允许离线拍摄+排队，上线后自动上传 |

### 12.6 Android权限矩阵

| **权限** | **用途** | **申请时机** | **用户拒绝的fallback** |
|---|---|---|---|
| POST_NOTIFICATIONS | 推送通知 | 首次启动引导 | 仅App内消息中心，失去离线推送 |
| CAMERA | 拍摄房源照片/定金凭证 | 首次点击拍照按钮时 | 提示用户从相册选择 |
| READ_MEDIA_IMAGES | 从相册选照片 | 首次点击相册按钮时 | 无法选择，只能拍照 |
| ACCESS_FINE_LOCATION | 开放日签到定位/小区地图 | 首次进入签到页/地图页 | 无法使用签到和地图 |
| CALL_PHONE | 一键拨号（可选） | 首次点击拨号按钮时 | 拷贝号码到剪贴板并跳转系统拨号盘 |
| READ_PHONE_STATE | 获取设备IMEI用于设备指纹 | 不申请 | 改用device_info_plus的Android ID（Android 10+推荐） |

### 12.7 强制更新策略

启动时检查版本：

```
App启动 → 上报 current_version_code → 后端对比 min_supported
  ├─ current_version_code < min_supported → 强制更新页（无法跳过）
  ├─ current_version_code < latest_version_code 且 force_update=false → 可选更新提示
  └─ current_version_code = latest_version_code → 正常进入
```
