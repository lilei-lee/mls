# 一、模块概述

带客协作是MLS系统的核心交互模块，覆盖从Buyer's Agent发起带客申请到实际带看完成的全过程。本模块实现两个核心目标：1.促成经纪人之间的高效合作带看。2.为交易留痕系统提供完整的证据链（节点②③④）。

> *核心设计原则：匿名申请（审批前双方不知道对方身份）→ 审批通过后身份互通 → 所有联络动作通过平台留痕。*

> *门店老板以经纪人身份参与带客协作时，与普通经纪人遵循完全相同的规则。*

# 二、带客申请（交易留痕节点②）

## 2.1 申请入口

Buyer's Agent在共享房源库详情页点击「申请带客」按钮，进入申请表单。

**App版UI设计**：
- 详情页底部固定栏包含「收藏」「申请带客」两个按钮
- 联卖审核未通过的经纪人「申请带客」按钮置灰+提示"请等待联卖权限审核通过"
- 处于暂停状态的经纪人按钮置灰+提示"当前账号暂停中，仅可操作进行中的交易"

## 2.2 申请表单

| **字段** | **说明** | **必填** |
|---|---|---|
| 客户姓氏 | 如 张 | 必填 |
| 客户性别 | 男/女 | 必填 |
| 购房需求描述 | 自由文本，如：三居室预算80-100万，看学区，全款 | 必填 |

> *客户电话不在申请表单中填写。平台不采集客户电话。*

**App版Flutter组件**：
- 客户姓氏：`TextField`（单字符限制）
- 客户性别：`ChoiceChip`（单选芯片，两个选项平铺）
- 购房需求：`TextField`多行+字数计数（最多200字）
- 提交按钮：`FilledButton` + 加载态（`CircularProgressIndicator`）

## 2.3 Listing Agent看到的信息

| **信息** | **是否可见** | **说明** |
|---|---|---|
| 客户姓氏 + 性别 | 可见 | 如 张先生 |
| 购房需求描述 | 可见 | 审批的核心依据 |
| 申请人姓名 | 不可见 | 匿名机制 |
| 申请人门店 | 不可见 | 匿名机制 |
| 申请人电话 | 不可见 | 匿名机制 |
| 客户电话 | 不可见 | 平台不采集 |

## 2.4 同一房源多方申请

同一套房源可以被任意数量的Buyer's Agent同时申请带客。Listing Agent对每个申请独立审批。同一个客户也可以被不同经纪人带去看同一套房。平台不做客户归属判定。**同一个BA也可以对同一房源提交多个带客申请（代表不同客户），每个申请独立审批。**

## 2.5 定金已付状态的申请

处于「定金已付」状态的房源仍然接受带客申请。系统在申请页面提示：该房源当前状态为定金已付，交易仍有可能变动。

**App版UI**：在申请表单顶部展示黄色警示条 + 图标（`Icons.warning_amber`）+ 文案"该房源已有客户付定金，建议作为backup带看"。

## 2.6 暂停挂牌状态的申请

处于「暂停挂牌」状态的房源不接受新的带客申请（房源不在共享库展示）。但暂停前已通过的带客申请保持有效，相关Buyer's Agent可以继续联络和安排带看。

## 2.6b LA被暂停时待审批申请的处理

Listing Agent被暂停使用期间，无法审批新的带客申请。同时房源标注「经纪人已暂停」不接受新申请。对于暂停前已提交但尚未审批的带客申请：

| **规则** | **说明** |
|---|---|
| 标记"审批暂停" | 系统自动将待审批申请状态标记为"审批暂停"，不计入审批超时统计 |
| 通知BA | 推送通知："Listing Agent暂时无法处理您的带客申请，预计X天后恢复"（X=暂停剩余天数） |
| 解除暂停后恢复 | LA暂停解除后，冻结的申请自动恢复为"待审批"状态，通知LA："您有X条积压的带客申请待处理" |
| 审计记录 | 冻结和恢复操作均记入audit_log |

> *与锁定状态（经纪人离职）的区别：锁定是永久性的，申请冻结等待移交给新LA。暂停是临时的，申请等LA恢复后自行处理，不涉及移交。例外：如果暂停期间发生归属变更，冻结的申请按归属变更规则处理（转移给新LA并标注来源），不再等待原LA解除暂停。归属变更优先级高于暂停冻结。*

## 2.7 LA自促成交的带客申请

Listing Agent自己找到买家时，以LA+BA双重身份走完整流程。系统检测到申请人（BA）和房源归属人（LA）是同一个user_id时：

| **步骤** | **系统行为** |
|---|---|
| BA发起带客申请 | 正常提交，填写客户姓氏/性别/需求（必填） |
| 审批环节 | 系统自动通过，跳过匿名机制和等待环节。不计入LA的"平均响应时间"统计。 |
| BA提交带看记录 | 上传带看照片（必填，实时相机拍摄），填写带看时间。**系统自动确认**，跳过LA确认等待环节。 |
| LA标记房源进入交易阶段 | 常规：标记「定金已付」并上传定金凭证。无定金交易：标记"无定金直接签约"并上传购房合同照片。自促成交不豁免。 |
| BA发起成交确认 | 填写成交价、成交日期等。房源必须处于定金已付/成交进行中。 |
| LA确认成交 | 独立填写成交价确认。自促场景下两次填价应一致。 |

> *LA实际只需操作4步：①填客户信息提交带客申请 → ②上传带看照片提交带看记录 → ③标记定金已付并上传凭证 → ④发起+确认成交。系统自动完成中间的审批和带看确认环节。留痕链完整覆盖节点②③④⑤⑥。7天有效期同样生效——自动通过审批后7天内需提交带看记录。*

# 三、申请审批（交易留痕节点③）

## 3.1 审批通知（App版渠道调整）

Listing Agent通过三层推送架构接收通知：

- **极光推送**：标题"新的带客申请"+内容"房源【北方明珠 2室1厅】有新带客申请，客户张先生，请审批"
- **微信服务号（如绑定）**：模板消息，点击跳转App
- **App内消息中心**：红点+列表展示

**Android推送动作按钮（V9新增）**：Android 7+支持在推送通知中直接嵌入操作按钮。系统通知展开后可直接操作：

```
┌─────────────────────────────────────┐
│ [MLS图标] 新的带客申请              │
│ 房源【北方明珠 2室1厅】             │
│ 客户张先生，需求三居预算80-100万    │
│ ┌──────────┐ ┌──────────┐          │
│ │   同意   │ │   拒绝   │          │
│ └──────────┘ └──────────┘          │
└─────────────────────────────────────┘
```

**交互规则**：
- 点击"同意"：直接通过审批，无需打开App（通过 `flutter_local_notifications` 的 `Notification Action`）。系统震动+Toast提示"已同意"。身份自动公开。
- 点击"拒绝"：打开App进入拒绝理由选择页（必须选理由，无法直接拒绝）
- 点击通知主体：打开App进入审批详情页

## 3.2 审批操作

| **操作** | **说明** |
|---|---|
| 同意 | 双方身份互相公开（姓名、门店），解锁一键拨号和申请加微信按钮。 |
| 拒绝 | 必须选择拒绝理由（下拉）+可选补充说明。双方身份不公开。 |

## 3.3 批量审批

当一套房源积累多条待审批申请时，Listing Agent可在「我的房源」管理页的待审批列表中进行批量操作：批量同意、批量拒绝。详见模块二V11第6.4节。

## 3.4 拒绝理由选项

| **理由** | **说明** |
|---|---|
| 客户需求与房源不匹配 | 如客户要三居但房源是两居 |
| 近期不方便看房 | 如房东出差/装修中等 |
| 房源即将成交 | 已有买家在走交易流程 |
| 其他 | 需填写补充说明 |

## 3.5 审批通过后的身份公开

审批通过后，双方在该条带客记录的上下文中互相可见：姓名、门店。同时解锁两个联络按钮。身份公开仅限于该条带客申请的关系中。

# 四、联络方式（V9 App版技术实现）

## 4.1 一键拨号

### 4.1.1 交互设计

点击「📞 一键拨号」按钮后：

1. 检查 `CALL_PHONE` 权限
   - 未授予 → 申请权限 + 文案说明"需要拨号权限以直接拨打对方电话"
   - 被拒绝 → 降级方案：复制号码到剪贴板 + 跳转系统拨号盘（号码预填）
2. 授予权限后：使用 `url_launcher` 调起 `tel:XXXXXXXXXXX`
3. 系统拨号盘弹出，用户确认拨号
4. 后端记录拨号动作（用户点击按钮即记录，不依赖是否真实通话）

### 4.1.2 技术实现

```dart
import 'package:url_launcher/url_launcher.dart';

Future<void> makeCall(String phone, String showingRequestId) async {
  // 1. 记录联络动作到后端
  await api.recordContact(
    contactType: 'phone_call',
    showingRequestId: showingRequestId,
  );
  
  // 2. 调起拨号盘
  final uri = Uri.parse('tel:$phone');
  if (await canLaunchUrl(uri)) {
    await launchUrl(uri);
  } else {
    // fallback: 复制到剪贴板
    Clipboard.setData(ClipboardData(text: phone));
    showToast('已复制电话号码');
  }
}
```

**留痕原则**：点击"一键拨号"按钮的动作本身就是留痕节点，不依赖是否真实拨通。决策汇总§2.6明确。

### 4.1.3 电话号码展示规则

- 号码**不直接在页面展示**（文字形式）
- 仅通过按钮形式呈现："📞 拨打 李明"
- 详情长按按钮可弹出完整号码+复制选项（兜底用）

# 五、带看确认（交易留痕节点④）

## 5.1 双方确认制

实际带看后，Buyer's Agent先提交带看记录，Listing Agent再确认。双方都确认后，带看记录正式生效。

## 5.2 Buyer's Agent提交（V9 App版重写）

### 5.2.1 提交表单

| **字段** | **说明** | **必填** |
|---|---|---|
| 带看时间 | 选择实际带看的日期和时间 | 必填 |
| 现场照片 | **至少1张实时相机拍摄的现场照片** | 必填（≥1张） |
| 带看备注 | 自由文本 | 选填 |

### 5.2.2 现场照片强制规则（防作弊）

**必须通过App内相机实时拍摄，不允许从相册选择**。

技术实现：

```dart
final XFile? photo = await ImagePicker().pickImage(
  source: ImageSource.camera,  // 只暴露相机入口
  imageQuality: 85,
  maxWidth: 1920,
);
```

**照片元数据要求**：
- EXIF拍摄时间：必须在提交前24小时内（过旧的照片拒绝上传）
- EXIF GPS坐标：必须开启定位权限以获取拍摄位置
- 照片hash存档：pHash记录到 showings 集合

### 5.2.3 GPS位置校验（V9新增）

拍摄时采集照片GPS坐标，与房源所在小区经纬度对比：

| **距离** | **系统动作** |
|---|---|
| ≤ 500m | 正常，标记 location_verified=true |
| 500m - 2000m | 允许提交，标记 location_suspicious=true，后台巡检 |
| > 2000m | 允许提交但标记 location_abnormal=true，后台优先审核，明显异常直接驳回 |
| GPS缺失 | 允许提交但标记 location_missing=true，信任度降级 |

**原则**：不在提交时强制拦截（考虑到地图坐标不准、室内信号弱等情况），而是后台后检+异常审查。

### 5.2.4 离线拍照排队

经纪人在弱网/离线场景下带看时：

```
用户拍摄照片 → 本地保存到Hive + 照片文件存应用专属目录
  ↓
状态标记：pending_upload
  ↓
联网检测（connectivity_plus监听）→ 自动触发上传队列
  ↓
上传成功 → 本地文件清理 + 状态更新为 submitted
  ↓
上传失败 → 保留本地文件 + 标记失败原因，允许用户手动重试
```

UI提示：拍照后立即显示"已保存，待上传"，联网后自动变为"上传中 → 上传完成"。

# 六、带看反馈（业务不变）

## 6.1 反馈触发

带看确认双方通过后，系统在24小时内向Buyer's Agent发送反馈请求通知（极光推送 + 消息中心）。

## 6.2 反馈表单

| **反馈项** | **选项** | **必填** |
|---|---|---|
| 客户对价格的看法 | 偏高/合理/偏低 | 必填 |
| 客户对房屋状况的看法 | 满意/一般/不满意 | 必填 |
| 客户购买意向 | 强/一般/弱/明确不考虑 | 必填 |
| 补充反馈 | 自由文本 | 选填 |

**App版UI**：使用 `ChoiceChip` 组呈现每个反馈项的选项，单选。补充反馈使用多行 `TextField`。

## 6.3 反馈可见性

Listing Agent可以看到每条反馈的完整内容（不看到反馈人身份）。其他经纪人在详情页只看到统计汇总。

# 七、开放看房日（Open House，V9 App版增强）

## 7.1 功能说明

Listing Agent可以为房源设置「开放看房日」——指定日期和时间段，期间经纪人可以自行到场看房评估，不需要提前提交带客申请。**开放看房日定位为Broker Open House，面向经纪人，不带客户。**

## 7.2 设置表单

| **字段** | **说明** | **必填** |
|---|---|---|
| 开放日期 | 选择日期 | 必填 |
| 开放时间段 | 如 14:00-17:00 | 必填 |
| 补充说明 | 如：请从北门进、带客请提前10分钟到 | 选填 |

**Flutter组件**：日期选择用 `showDatePicker`，时间段用两个 `showTimePicker`。

## 7.3 展示与通知

设置开放看房日后，该房源在共享库卡片上显示「开放日」标签和日期时间。收藏了该房源的经纪人收到通知（极光推送 + 消息中心）。

### 7.3.1 本地日历订阅（V9新增）

收到开放日通知后，App允许经纪人一键添加到系统日历：

```dart
import 'package:add_2_calendar/add_2_calendar.dart';

Add2Calendar.addEvent2Cal(Event(
  title: '开放日：${communityName} ${buildingInfo}',
  description: '房源：${mlsId}\n备注：${notes}',
  location: '${communityAddress}',
  startDate: openHouseStart,
  endDate: openHouseEnd,
  allDay: false,
));
```

用户确认后，事件加入系统日历，到期日历App自动提醒。

### 7.3.2 本地通知提前提醒（V9新增）

注册本地通知（`flutter_local_notifications`）：
- **开放日前1天20:00**：预告提醒"明天下午14:00-17:00北方明珠开放日，别忘了去踩点"
- **开放日前1小时**：出发提醒"1小时后北方明珠开放日开始"

即使App被杀，系统级本地通知仍能到达（条件：App未卸载）。

## 7.4 状态变更时自动取消开放日

当房源发生**任何状态变更**时（包括但不限于：在售→暂停挂牌、在售→定金已付、在售→成交进行中、在售→撤牌、归属变更），如果有未来的开放看房日，系统自动取消该开放日，并通知所有已收到开放日通知的经纪人（详见模块七）。取消操作记入audit_log。

**App版附加动作**：如用户已添加到系统日历，App无法直接删除用户日历（iOS/Android没有跨App删除权限），但推送中文案明确"原定X月X日的开放看房日已取消，请更新您的日历"。

## 7.5 签到与留痕（V9 App版增强）

开放看房日定位为**Broker Open House**——经纪人自己到场看房评估，不带客户。

### 7.5.1 地理围栏触发签到（V9新增）

当经纪人携带App接近开放日房源时：

```
App后台定位（需用户授权 ACCESS_BACKGROUND_LOCATION，选填）
  ↓
经纪人进入以房源小区坐标为中心、100m半径的地理围栏
  ↓
App收到围栏进入事件
  ↓
如该时段正好是开放日 → 本地通知弹出"您已靠近北方明珠，点击签到"
  ↓
用户点击 → 跳转签到页
```

**替代方案**（用户未授予后台定位权限时）：
- App前台打开时，工作台顶部提示"附近有进行中的开放日：北方明珠"
- 点击进入签到页

### 7.5.2 签到流程

```
进入签到页
  ↓
1. 校验当前时间在开放日时段内（否则提示"不在签到时段"）
  ↓
2. 获取当前位置（前台定位）
  ↓
3. 校验位置距离房源小区 ≤ 200m（否则提示"请到现场后再签到"）
  ↓
4. 展示房源基本信息 + [确认签到]按钮
  ↓
5. 点击签到 → 拍摄1张现场照片（可选但推荐）→ 提交
  ↓
6. 后端记录 open_house_checkins（含listing_cycle、GPS、签到时间、照片URL）
```

### 7.5.3 签到数据结构

| **字段** | **说明** |
|---|---|
| agent_id | 签到经纪人 |
| open_house_id | 开放日ID |
| house_id | 房源ID |
| listing_cycle | 挂牌周期序号 |
| checkin_at | 签到时间 |
| gps_lat / gps_lng | 签到GPS坐标 |
| distance_to_community | 距离小区中心米数 |
| checkin_photo_url | 签到照片（可选） |

### 7.5.4 签到可见性

**签到不等同于带客申请或带看确认**。签到只记录"该经纪人看过这套房"。如果经纪人评估后认为适合推荐给客户，后续仍需走正常的带客申请流程（第二节）。

Listing Agent可在签到列表中查看所有到场经纪人（此时身份公开）。**签到经纪人之间互不可见——签到列表仅Listing Agent可见，各经纪人只能看到自己的签到状态，不能看到其他签到人的信息。**

> *这是B2B平台的Broker Open House。经纪人来踩点是为了评估房源是否值得推荐给自己的客户。签到数据帮助Listing Agent了解同行对房源的关注度。*

# 八、申请有效期与提醒

## 8.1 有效期规则

带客申请通过后，BA有**7天**时间**提交带看记录**（BA单方操作即可）。提交后申请视为有效，后续LA确认不受7天约束。超过7天未提交带看记录，申请自动失效。

| **时间节点** | **系统动作** | **通知方式（App版）** |
|---|---|---|
| 通过后第5天 | 提醒BA："您有X组带客申请将在2天后过期，请尽快安排带看" | 极光推送 + 消息中心 |
| 通过后第7天 | 申请自动失效，状态变为"已过期"。双方身份恢复隐藏。 | 极光推送 + 服务号 + 消息中心（通知BA和LA） |

过期后BA如仍需带看，需重新提交带客申请，走正常审批流程。过期操作记入audit_log。

**计时暂停**：房源进入暂停挂牌或锁定状态期间，7天有效期计时暂停（房东不便看房，BA无法完成带看不应被扣时间）。恢复在售后计时继续。与DOM暂停逻辑一致。

**归属变更重置**：归属变更时被转移的已通过申请，7天有效期从转移时刻重新计算（换了LA等于新的合作关系起点）。

## 8.2 关闭申请

BA也可以在7天有效期内手动提前关闭申请，需选择关闭原因。关闭操作记入audit_log。关闭后不影响重新申请。关闭后系统通知Listing Agent（极光推送+消息中心），告知该组带客申请已被主动关闭。

# 九、App内实时状态同步（V9新增）

## 9.1 工作台角标实时更新

底部Tab的"工作台"图标展示待处理数（红点+数字）：

- 新带客申请到达 → 推送触发 → App更新本地数据 → 角标+1
- 成交确认到达 → 同上
- 带看确认到达 → 同上
- 用户处理完毕 → 手动触发减1 + 重新拉取兜底

**技术实现**：
- 使用 `Riverpod` 状态管理，`badgeCountProvider` 作为全局状态
- 推送接收到新事件时 `badgeCountProvider.notifier.increment()`
- App启动时主动拉取 `GET /api/dashboard/pending-count` 校准

## 9.2 推送到达后的即时反馈

推送到达App时：
- 如App在前台：
  - 顶部滑出悬浮通知条（`flutter_local_notifications` 的 in-app 风格）
  - 工作台相关区块刷新数据
  - 震动提醒（可关闭）
- 如App在后台：系统通知栏显示，点击直达目标页
- 如App被杀：厂商通道触发系统通知

## 9.3 数据同步策略

| **场景** | **同步方式** |
|---|---|
| App冷启动 | 拉取最近未读消息 + 待处理事项 + 工作台数据 |
| 从后台切回前台 | 基于 `last_active_at` 增量拉取变更 |
| 下拉刷新 | 强制重新拉取当前页面数据 |
| 推送到达 | 对应数据自动失效+下次访问时重新拉取 |

暂不实现WebSocket长连接（种子期用户规模小，轮询+推送即可；后期房源量上千后可考虑升级）。
