# 一、App安装与首次启动流程

## 1.1 标准启动流程

```
用户从应用商店安装App
  ↓
点击App图标启动
  ↓
启动页（Splash，Logo+加载动画，最长1.5秒）
  ↓
版本检查
  ├─ 低于最低支持版本 → 强制更新页（无法跳过）
  ├─ 有新版本且非强制 → 可选更新提示（可忽略）
  └─ 版本正常 → 继续
  ↓
首次启动？
  ├─ 是 → 隐私政策与用户协议页（必须同意）→ 登录页
  └─ 否 → 检查登录态
          ├─ 无有效token → 登录页
          ├─ token有效且启用生物识别 → 生物识别验证 → 工作台
          └─ token有效未启用生物识别 → 直接进入工作台
```

## 1.2 隐私政策与用户协议

首次启动时强制展示以下内容，用户必须同意才能继续：

- 《用户服务协议》（说明平台性质、使用规则、违规处理）
- 《隐私政策》（说明收集的个人信息类别、使用方式、第三方SDK清单）
- 《第三方SDK清单》（极光推送、微信开放平台、高德地图、腾讯云COS、阿里云/腾讯云短信）

用户可在设置页随时查阅。法律合规性要求（《个人信息保护法》《网络安全法》）。

## 1.3 Android权限引导

首次启动登录完成后，引导用户授予通知权限（Android 13+必须）：

- 弹窗说明："为了及时接收带客申请、成交确认等关键通知，请允许发送通知"
- 调用 `permission_handler` 请求 `POST_NOTIFICATIONS`
- 用户拒绝后，在工作台顶部展示"通知已关闭，可能错过重要业务消息"提示条

其他权限（相机、相册、定位、拨号）按需在首次使用场景时申请，不在启动时一次性索要。详见本模块第十二节「Android权限矩阵」。

# 二、注册流程（V8重写）

## 2.1 主路径：手机号+短信验证码注册

```
登录页 → 输入手机号 → 点击"获取验证码"
  ↓
后端校验手机号 → 阿里云/腾讯云短信下发6位验证码（有效期5分钟）
  ↓
用户输入验证码 → 点击"登录/注册"
  ↓
后端校验验证码 → 查询agents集合
  ├─ 手机号已注册 → 登录成功 → 工作台
  └─ 手机号未注册 → 进入注册信息填写页
                    ↓
                    填写姓名、身份证号、所属门店、服务区域等
                    ↓
                    提交注册 → 创建agents记录 → 立即可使用基础功能
                    ↓
                    工作台（展示"联卖权限待审核"提示条，种子期自动通过）
```

**联卖权限审核结果通知**：通过极光推送+服务号（如已绑定）+App内消息中心三通道触达（详见模块七）。

## 2.2 辅助路径：微信开放平台登录

前提：用户已完成首次手机号注册并在"账户设置"中绑定微信。

```
登录页 → 点击"微信登录"按钮
  ↓
fluwx唤起微信App授权
  ↓
微信返回 code → 后端用 code 换取 access_token + openid + UnionID
  ↓
后端查询 wechat_bindings 集合
  ├─ UnionID 已绑定到某个 agent → 返回JWT → 登录成功 → 工作台
  └─ UnionID 未绑定 → 提示"请先用手机号登录后在账户设置中绑定微信"
```

**微信绑定的价值**：
- 登录便捷：后续可直接微信一键登录
- 服务号推送：UnionID打通微信服务号通道，收到服务号通知
- 分享能力：分享房源到微信聊天/朋友圈
- 快捷跳转：微信通知点击可一键唤起App

**微信绑定不强制**：即使不绑定微信也能正常使用App全部功能，只是失去服务号推送通道和分享到微信的能力。

## 2.3 验证码规则

| **规则** | **说明** |
|---|---|
| 格式 | 6位纯数字 |
| 有效期 | 5分钟 |
| 重试间隔 | 同一手机号60秒内不可重复获取 |
| 每日上限 | 同一手机号每日最多10条 |
| IP上限 | 同一IP每日最多50条（防刷） |
| 错误锁定 | 连续3次输入错误锁定手机号15分钟 |
| 签名+模板 | 签名"张家口MLS"，模板："您的验证码是XXXXXX，5分钟内有效，请勿泄露。" |

# 四、门店与经纪人层级关系（不变）

参考美国MLS的Broker-Agent层级结构，系统支持门店与经纪人的从属关系。

## 4.1 两种账号类型

| **类型** | **门店账号（Broker）** | **经纪人账号（Agent）** |
|---|---|---|
| 注册人 | 门店老板/负责人 | 个人经纪人 |
| 经纪人身份 | 同时具备完整的经纪人身份，可以直接参与业务 | 独立经纪人身份 |
| 核心功能 | 全部经纪人功能 + 查看名下所有经纪人的房源/带客/成交数据 + 管理下属 + 导出门店整体数据 | 录入房源、浏览库、发起/接收带客申请、交易留痕 |
| 绑定方式 | 注册后生成门店邀请码，发给下属经纪人 | 注册时输入邀请码绑定，或选"独立经纪人" |

> *门店老板同时具备完整的经纪人身份。店老板可以自己录入房源、发起和接收带客申请、参与交易留痕——与普通经纪人拥有完全相同的业务能力，同时额外拥有门店管理功能。*

## 4.2 门店老板账号角色切换

门店老板登录App后，工作台顶部展示角色切换器："门店管理" / "个人经纪人"。两个角色的功能完全隔离：

| **角色** | **功能范围** | **处罚影响** |
|---|---|---|
| 门店管理 | 查看名下经纪人数据、管理下属、房源移交、导出门店数据 | 不受处罚影响，始终可用 |
| 个人经纪人 | 录入房源、浏览共享库、带客申请、交易留痕、个人数据导出 | 处罚只禁用此入口 |

**技术实现**：同一个user_id，两个role维度，处罚标记只作用于agent_role。角色切换通过Riverpod状态切换，无需重新登录。

## 4.3 门店账号注册信息

| **字段** | **说明** | **必填** |
|---|---|---|
| 门店名称 | 官方全称 | 必填 |
| 负责人姓名 | 门店老板真实姓名 | 必填 |
| 负责人身份证 | 实名认证 | 必填 |
| 负责人手机 | **短信验证码登录流程自动带入** | 必填（自动） |
| 门店地址 | 实体门店地址 | 必填 |
| 服务区域 | 桥东/桥西/万全/经开，可多选 | 必填 |
| 营业执照 | 相机拍摄或相册选择上传，用于审核 | 选填 |

门店老板注册门店账号后，系统自动为其创建一个经纪人身份（与门店账号共享同一个登录入口），无需单独再注册经纪人账号。

## 4.4 门店账号的管理能力

**经纪人功能**：门店老板拥有全部经纪人功能——录入房源、浏览共享库、发起/接收带客申请、交易留痕、导出个人数据。

**门店管理功能（额外）**：

- **查看数据**：名下所有经纪人的房源、带客、成交数据。门店管理视图包含门店老板自己的经纪人数据——老板被暂停后通过门店管理入口仍可查看自己的历史数据。
- **管理下属**：查看名下经纪人列表、移除经纪人（解除绑定，变为独立经纪人）。
- **房源移交**：将名下离职经纪人的房源重新分配给其他经纪人（详见第八节）。
- **数据导出**：导出门店整体数据报表，Excel格式，通过邮件发送到老板邮箱（App不直接处理大文件下载）。

## 4.5 独立经纪人

不属于任何门店的经纪人选择"独立经纪人"。后期可输入邀请码重新绑定门店。

# 五、权限分层（不变）

基础权限（注册即可用）和联卖权限（需后台审核通过）。

**种子期快速模式**：后台设置"注册即开通联卖"开关。种子期开启此开关，注册即自动通过联卖审核，不需要后台逐个审核。正式期关闭此开关恢复审核制。开关状态变更记入audit_log。

| **功能** | **注册即可用** | **审核后** |
|---|---|---|
| 录入房源 | ✔ | ✔ |
| 浏览共享房源库 | ✔ | ✔ |
| 发起带客申请 | ✖ | ✔ |
| 接收带客申请 | ✖ | ✔ |
| 申请看房 | ✖ | ✔ |
| 交易留痕 | ✖ | ✔ |
| 导出数据 | ✔ | ✔ |
| 开放联卖（房源对外可见） | ✖ | ✔ |

> *联卖审核通过前，经纪人录入房源时「是否开放联卖」开关强制关闭且不可手动开启。房源仅自己可见，不进入共享库。审核通过后开关自动解锁，经纪人可自行选择是否开放。*

# 六、登录态管理（V8新增）

## 6.1 JWT Token机制

- **Access Token**：有效期2小时，存储在 `flutter_secure_storage`（Android Keystore加密）
- **Refresh Token**：有效期30天，同样加密存储
- **自动续期**：Access Token过期前5分钟，App自动用Refresh Token换取新Access Token，用户无感

## 6.2 生物识别登录

**启用条件**：账号已通过手机号完成至少一次登录，用户在"账户安全"中主动启用。

**启用流程**：

```
用户点击"启用指纹登录"
  ↓
local_auth 检测设备是否支持（指纹/面部识别）
  ├─ 不支持 → 提示"此设备不支持生物识别"
  └─ 支持 → 调起系统生物识别弹窗
          ↓
          识别成功 → 将当前 refresh_token 用生物识别密钥加密后存入 flutter_secure_storage
          ↓
          启用成功
```

**使用流程**：

```
App启动 → 检测到已启用生物识别 → 调起系统识别弹窗
  ├─ 识别成功 → 取出加密 refresh_token → 后端换取 access_token → 工作台
  ├─ 识别失败3次 → 禁用生物识别24小时 → 强制手机号验证码登录
  └─ 用户选择"跳过，用手机号登录" → 登录页
```

**自动禁用场景**：
- 账号更换手机号（生物识别密钥与原手机号绑定）
- App卸载重装（secure storage数据丢失）
- 连续3次识别失败（24小时锁定）
- 账号密码变更（安全策略）

## 6.3 多设备登录策略

- **同时在线上限**：3台设备
- **第4台登录**：踢掉最早登录的设备（最后活跃时间最早的）
- **被踢设备体验**：收到推送"您的账号在其他设备登录，本设备已自动登出"，打开App自动回到登录页
- **用户可手动管理**：在"账户安全"→"登录设备"中查看所有在线设备，可主动登出任意设备

## 6.4 异地登录二次验证

**触发条件**：登录时检测到本次登录IP所属省份与最近一次登录不同。

**验证方式**：
- 短信验证码（主）
- 已绑定微信时，推送到微信的人工确认（备）

**验证失败**：拦截登录，记录 `login_log.failure_reason = "异地验证失败"`，提醒账号主人注意。

## 6.5 设备信任

首次登录的新设备触发：

```
新设备登录
  ↓
设备指纹生成（device_info_plus 采集设备型号、系统版本、Android ID等）
  ↓
记录到 user_devices（is_trusted = false）
  ↓
要求短信验证码二次验证
  ├─ 验证通过 → is_trusted = true → 登录成功
  └─ 验证失败 → 拦截登录，记录异常
```

信任设备在"账户安全"→"登录设备"中可查看设备型号、最后登录时间、IP、可主动移除信任。

## 6.6 登出与账号注销

**登出**：清除本地 Access Token + Refresh Token + 生物识别密钥，退回登录页。其他设备的会话不受影响。

**账号注销**：需在App内发起申请，后台审核（检查是否有进行中的交易、未结算奖金、未处理争议）。审核通过后：
- agents.status 标记为 deleted
- 个人信息匿名化处理（姓名改为"已注销用户"，手机号置空）
- 历史交易留痕保留（供另一方维权和审计）
- 30天内可撤销注销申请
- 30天后永久删除可删除部分，保留审计必要数据

# 七、App首页工作台（V8调整）

## 7.1 设计说明

经纪人登录后的首页是个人工作台（仪表盘），而非直接进入共享房源库。工作台展示待处理事项和快捷入口，帮助经纪人快速了解当前状态。

**Flutter技术实现**：工作台页为根路由，底部Tab导航（工作台/房源库/消息/我的），使用 `go_router` 管理，支持推送深度链接直达。

## 7.2 工作台内容

| **区块** | **展示内容** |
|---|---|
| 顶部问候与角色切换 | "早上好，XXX" + 门店老板可见角色切换器（门店管理/个人经纪人） |
| 待处理事项 | 待审批的带客申请数（角标）、待确认的带看记录数、待确认的成交数、待结算的奖金数 |
| 快捷入口 | 录入房源、我的房源、共享房源库、消息中心 |
| 我的数据摘要 | 当前在售房源数、本月带客申请数、本月成交数 |
| 最新动态 | 最近3条与自己相关的通知摘要（点击进入消息中心） |
| 顶部提示条（按需） | "通知权限已关闭"/"联卖审核中"/"有新版本可更新"/"建议关注服务号加强消息触达" |

## 7.3 弱网/离线表现

- 工作台数据用 Hive 本地缓存最近一次拉取
- 弱网/离线时展示缓存数据 + 顶部黄色标签"当前为离线缓存，X分钟前更新"
- 下拉刷新强制联网重新拉取
- 上线后自动增量同步

> *参考美国MLS的Agent Dashboard。首页不是房源列表，而是工作台——让经纪人第一眼看到自己该做什么，而不是被动浏览。共享房源库作为底部Tab之一，随时可切换。*

# 八、经纪人离职与房源移交（业务不变）

## 8.1 场景说明

经纪人离开门店或不再从事经纪业务时，其名下房源需要有明确的处理机制，保护房东利益。

## 8.2 处理规则

| **场景** | **触发方式** | **房源处理** |
|---|---|---|
| 经纪人离开门店（解除绑定） | 门店老板在管理页操作移除 | 该经纪人名下房源自动锁定，门店老板可将房源重新分配给门店内其他经纪人 |
| 经纪人主动注销或长期不活跃 | 后台操作 | 房源自动锁定，后台可指定新的归属经纪人 |
| 独立经纪人离开（无门店老板） | 后台操作 | 房源进入「已下架」状态，如有独家委托，后台通知房东联系平台重新委托 |

## 8.3 房源锁定状态

经纪人离职后房源进入「锁定」状态：共享库仍展示（保护房东利益），标注「经纪人已离职，待移交」（**灰色标签，区别于三级暂停的红色「经纪人已暂停」标签**），不接受新的带客申请，已通过的带客申请保持有效。

锁定期间待审批的带客申请进入冻结状态，不计入审批超时。房源移交完成后，冻结的待审批申请自动转给新Listing Agent，申请人收到通知。

## 8.4 移交流程

门店老板在App的"门店管理"入口：

```
门店管理 → 离职经纪人列表 → 选择锁定房源
  ↓
选择接收人（门店内其他经纪人列表）
  ↓
推送通知给接收人："门店老板将房源【XXX】移交给您"
  ↓
接收人在工作台"待处理"中确认接收
  ↓
归属转移完成，移交操作记入audit_log
```

## 8.5 未完成交易的处理

离职经纪人名下如有未完成的交易（已有带看记录但未成交），交易数据保留供另一方维权。如果有未结算的合作奖金，结算单标记为「需人工介入」，后台主动跟进。

> *参考美国MLS的Listing Transfer机制。经纪人离职是必然发生的场景，不设计处理机制会导致房东利益受损。*

# 十、处罚与封禁（业务不变，登录机制适配）

> *统一使用模块五的四级处罚体系（警告/公示+功能限制/暂停使用/永久踢出），确保全系统处罚标准一致。*

处罚体系的完整定义、适用情形、功能限制细则、暂停期间规则、永久踢出规则均详见模块五第八节。

本模块仅记录处罚对经纪人账号状态的影响：

| **处罚等级** | **账号状态** | **房源处理** | **登录限制（App版）** | **恢复方式** |
|---|---|---|---|---|
| 一级（警告） | 正常 | 不影响 | 无限制 | 无需恢复 |
| 二级（公示） | 正常+标签 | 不影响，经纪人主页标注「有违规记录」 | 无登录限制 | 处罚执行完毕后12个月自动移除 |
| 三级（暂停） | 暂停 | 房源保留，标注「经纪人已暂停」，不接受新带客申请 | **可登录，生物识别/微信登录/验证码登录均可正常使用，登录后仅可操作进行中的项目** | 暂停期满自动恢复 |
| 四级（踢出） | 已踢出 | 所有房源自动下架。未完成交易进入保护性处理 | **所有登录方式拦截，登录页提示"账号已禁用，如有异议请联系平台"。生物识别凭据自动清除。** | 不可恢复，不可重新注册（同一身份证号拦截） |

> *暂停期间经纪人可以登录App，但仅能操作交易进行中的项目（确认成交/奖金结算/带看确认/争议答辩），其他所有功能禁用。门店老板的「门店管理」入口不受影响。房源保留只是为了不殃及无辜的房东。*

## 10.1 暂停/踢出时未完成交易的处理

参考美国MLS机制，交易不因经纪人的处罚而中断。

**三级暂停**：暂停期间经纪人可以登录操作交易进行中的项目。具体可操作范围详见模块五第8.3节。

**四级踢出**：

| **场景** | **处理方式** |
|---|---|
| 被踢出者是门店经纪人 | 未完成交易转给门店老板代为处理。门店老板可代完成成交确认、奖金结算确认。 |
| 被踢出者是独立经纪人 | 未完成交易标记「需人工介入」，后台主动跟进。**后台可代为完成成交确认操作。** |
| 被踢出者是门店老板 | 经纪人入口永久禁用，**门店管理入口永久保留**。未完成的个人经纪人交易标记「需人工介入」，后台主动跟进。 |
| 对方的举报权利 | 被踢出者无法登录不影响另一方的举报权利，后台直接受理。 |
| 后台代确认 | 任何一方在成交确认流程中被暂停/踢出导致流程卡住，另一方可申请后台代为完成确认操作。 |

> *核心原则：处罚是对违规经纪人的惩罚，不应伤害无辜的合作方。已经在进行的交易必须有路径走完。门店管理权是财产权而非业务权限，不因个人违规剥夺。*

## 10.2 踢出后重注册拦截

- 同一身份证号拦截：踢出处罚记录永久保留，同一身份证号再次注册时拒绝
- 同一手机号拦截：12个月内同一手机号无法重新注册
- 设备指纹拦截：device_id 记入黑名单，同一设备注册新账号时标记为"高风险"由后台审核

## 13.1 版本检查机制

App启动时向后端查询 `app_versions` 集合：

```
GET /api/app/version-check
  ↓
响应：{
  latest_version_code: 110,
  latest_version_name: "1.1.0",
  min_supported_version_code: 100,
  force_update: false,
  rollout_percentage: 50,

  download_url: "https://www.zjkmls.com/download/v1.1.0.apk"
}
  ↓
本地 current_version_code 对比：
  ├─ current < min_supported → 强制更新页（全屏，只有"更新"按钮）
  ├─ current < latest 且 force_update=false → 顶部红点提示+工作台提示条
  └─ current = latest → 正常进入
```

## 13.2 灰度发布

新版本发布时 `rollout_percentage` 从10开始，根据用户user_id hash判断是否收到更新提示，逐步放量到100%。崩溃率异常时可快速回滚（调低百分比）。
