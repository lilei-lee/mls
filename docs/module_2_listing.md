# 一、房源录入字段（业务不变）

## 1.1 基础信息

| **字段** | **说明** | **必填** |
|---|---|---|
| 小区名称 | 从小区库搜索选择，库里没有可手动添加 | 必填 |
| 楼栋号 | 如 3号楼 | 必填 |
| 单元 | 如 2单元 | 必填 |
| 楼层/总楼层 | 如 6/18 | 必填 |
| 房号 | 如 602，用于查重 | 必填 |
| 户型 | 几室几厅几卫 | 必填 |
| 建筑面积 | 平方米 | 必填 |
| 朝向 | 南/北/东/西/南北通透等 | 必填 |

## 1.2 价格信息

| **字段** | **说明** | **必填** |
|---|---|---|
| 总价 | 万元，手动填写 | 必填 |
| 单价 | 元/㎡，系统自动计算（总价÷面积） | 自动计算 |
| 付款方式 | 全款/贷款，指房东要求的付款方式 | 必填 |

## 1.3 房源详情

| **字段** | **说明** | **必填** |
|---|---|---|
| 房屋现状 | 毛坯/简装/精装 | 必填 |
| 房本状态 | 有本/在途/抵押 | 必填 |
| 产权年限 | 70年/40年/其他 | 必填 |
| 房东出售原因 | 换房/急用钱/其他 | 选填 |

## 1.4 房屋状况披露

参考美国MLS的Property Disclosure机制。Listing Agent必须如实披露房屋已知问题，帮助Buyer's Agent提前识别风险，减少无效带看。

| **披露项** | **说明** | **填写方式** |
|---|---|---|
| 是否漏水 | 屋顶、墙面、管道等是否有漏水情况 | 是/否/不确定 |
| 是否有违建/改建 | 是否存在未经审批的改建、加建、封阳台等 | 是/否/不确定 |
| 是否有产权纠纷 | 是否涉及继承、离婚析产、共有人争议等 | 是/否/不确定 |
| 是否凶宅 | 房屋内是否发生过非正常死亡事件 | 是/否/不确定 |
| 是否有欠费 | 物业费、供暖费、水电费等是否有欠缴 | 是/否/不确定 |
| 补充说明 | 对以上任何「是」或「不确定」的项目进行补充说明 | 自由文本，选填 |

## 1.5 备注字段

备注拆分为两个独立字段，参考美国MLS的Agent Remarks和Private Remarks机制：

| **字段** | **说明** | **可见范围** |
|---|---|---|
| 联卖备注 | 所有经纪人可见。如：房东急售价格可谈、仅周末可看房 | 所有经纪人 |
| 个人备注 | 仅自己可见的私人笔记。如：房东心理价68万 | 仅自己 |

## 1.6 看房方式

| **字段** | **说明** | **必填** |
|---|---|---|
| 看房条件 | 下拉选择：空置可随时看 / 有人居住需预约 / 有租客需提前通知 / 房东要求在场 | 必填 |
| 看房补充说明 | 自由文本，如：房东下午6点后才方便、有宠物进门注意 | 选填 |

## 1.7 图片与委托

| **字段** | **说明** | **必填** |
|---|---|---|
| 实拍照片 | 至少3张 | 必填（≥3张） |
| 独家委托协议 | 拍照上传，种子期不强制（后台可配置）。「即将上市」状态必须上传。 | 条件必填 |
| 委托到期日 | 有委托时必填，到期自动下架（含7天宽限期） | 条件必填 |

> *照片存储：照片URL存在独立集合house_photos（字段：house_id、photo_url、photo_type[实拍/委托/定金凭证]、upload_cycle[挂牌周期序号]、created_at），通过house_id关联。houses集合只存结构化数据，不存照片URL。每个挂牌周期的照片独立管理，重新上架时旧周期照片保留（只读），新周期照片重新上传。*

## 1.8 联卖设置

| **字段** | **说明** | **必填** |
|---|---|---|
| 是否开放联卖 | 开/关，关闭后仅自己可见。**联卖审核未通过的经纪人此开关强制关闭且不可手动开启。** | 必填（默认开） |
| 合作奖金 | 金额（元），0=无奖金。**设定后可上调或下调。调整时系统强制通知所有已通过的BA（含已带看和未带看）和收藏者（详见模块七）。待审批的BA不通知。已提交成交确认的交易不受影响（锁定BA提交时的值）。** | 选填（默认0） |

> *联卖开关与经纪人的联卖审核状态联动。审核未通过前强制关闭，房源仅自己可见不进入共享库。审核通过后自动解锁，已录入的房源开关自动切为「开」。*

> *奖金调整规则：可自由调整（上调/下调），但调整有通知义务——系统自动向已通过的BA（含已带看和未带看）和收藏者推送。待审批的BA不通知。已提交的成交确认中奖金金额锁定为BA提交时的值。奖金每次变动记入bonus_history（含listing_cycle字段标识周期）。归属变更时奖金重置为0，新归属人自行设定后遵循同样规则。*

# 二、MLS编号

每套房源录入时系统自动生成唯一的MLS编号，格式如ZJK-20260401-001。经纪人之间沟通时直接用编号指代房源，提高效率。

# 三、独家委托策略

## 3.1 后台可配置开关

| **配置项** | **说明** |
|---|---|
| 上架是否必须上传委托协议 | 种子期「否」，正式期可切「是」 |
| 无委托房源是否可联卖 | 种子期「是」，正式期可切「否」 |

无委托房源在列表显示「未验证」标签。

## 3.2 「即将上市」状态的特殊规则

使用「即将上市」状态时，独家委托协议为强制必填，不受上述开关控制。此规则不可关闭。

> *设计意图：「即将上市」的唯一目的是凭独家协议先占归属。没有协议就不存在「先占」的合理性，直接用「在售」状态即可。*

## 3.3 委托到期提醒与宽限期（App版渠道调整）

| **时间节点** | **系统动作** | **通知方式（App版）** |
|---|---|---|
| 委托到期前14天 | 发送第一次到期提醒 | 极光推送 + 消息中心 + **本地通知兜底**（V11新增） |
| 委托到期前3天 | 发送第二次到期提醒 | 极光推送 + 服务号（如绑定）+ 消息中心 + 本地通知兜底 |
| 委托到期日 | 房源自动下架，进入7天宽限期 | 极光推送 + 服务号（如绑定）+ 消息中心 |
| 宽限期内（7天） | 经纪人可上传新委托协议恢复上架，不需要重新录入房源信息 | — |
| 宽限期结束 | 房源状态变为「已下架」，如需重新上架需上传新委托后手动操作 | 消息中心 |

> *V11新增本地通知兜底：委托到期提醒属于高优先级提醒，App启用后端推送的同时，使用 `flutter_local_notifications` 在客户端本地设置基于到期时间的本地通知（如到期前14天/3天的固定时刻），作为推送失败时的兜底。即使用户长时间未打开App，本地通知仍能触发系统提醒（条件：App未被卸载）。*

# 四、房源查重与归属判定

## 4.1 查重逻辑与楼盘字典

系统根据「小区+楼栋+单元+楼层+房号」五字段自动查重。**唯一索引永远生效——每套物理房屋在houses集合中永远只有一条记录（一户一码），不因状态变化而新增或删除。**

| **场景** | **处理方式** |
|---|---|
| 录入时无匹配 | 新建房源记录，生成MLS编号 |
| 录入时匹配到活跃状态房源 | 提示"该房源已被录入，当前归属人为XXX"，不可重复录入 |
| 录入时匹配到已售/撤牌/已下架房源 | 提示"该房源曾挂牌，可申请重新上架"，进入**重新上架流程**（见4.1b） |

> *一户一码是楼盘字典的基础。同一套房无论经历多少次买卖，MLS编号不变，所有历史（上市历史、成交历史、价格历史、带看历史）永久串联在同一条记录下。这是MLS最核心的数据资产。*

## 4.1b 已售/撤牌房源重新上架

任何经纪人搜索到已售/撤牌/已下架的房源后，可以申请重新上架。重新上架不是"新建房源"，而是在同一条房源记录上开启新的挂牌周期。

| **步骤** | **操作** |
|---|---|
| 1 | 经纪人搜索到目标房源（通过小区+楼栋+单元+房号或MLS编号） |
| 2 | 系统展示该房源的历史信息（上次成交价、成交时间等），提示"该房源当前状态为已售/撤牌，可申请重新上架" |
| 3 | 经纪人点击"申请重新上架"→ 重新填写所有可变字段→ 提交 |
| 4 | 系统走正常归属判定：先到先得。如有其他经纪人同时申请，独家委托优先。**原经纪人无优先权。** |
| 5 | 上架成功后：房源状态变为「在售」（或「即将上市」——前提是该房源此前从未用过即将上市状态），listing_history追加新记录，DOM从零重新开始，首次上架日期更新为本次上架时间。触发"关注小区新房源上架"通知（详见模块七）。 |

**重新上架时的字段处理：**

| **字段类型** | **处理方式** | **示例** |
|---|---|---|
| 不变属性（自动保留） | 系统自动带出，不可修改 | 小区、楼栋、单元、楼层、房号、建筑面积、户型、朝向、产权年限 |
| 可变属性（重新填写） | 清空旧值，经纪人必须重新填写 | 总价、房屋现状、房本状态、看房条件、实拍照片、房屋状况披露 |
| 新周期属性（全部重置） | 系统自动重置 | 合作奖金（重置为0）、联卖备注（清空）、个人备注（清空）、DOM（从零开始）、收藏计数（重置为0） |
| 收藏记录（清除+通知） | 删除旧周期的favorites记录，favorite_count重置为0，通知原收藏者 | favorites集合中该house_id的记录 |
| 历史数据（永久保留） | 只读展示，不可修改 | listing_history、price_history、bonus_history、成交记录、带看记录 |

> *冻结申请处理：如果房源因暂停超时自动撤牌导致带客申请处于冻结状态，且重新上架的经纪人不是原归属人，系统自动关闭所有冻结的带客申请，并通知相关BA重新提交。如果是原归属人自己恢复上架，则按原规则解冻并通知BA。*

## 4.2 归属规则

默认：先到先得。同一套房谁先录入就归谁。

例外：独家协议大于先到先得。后录入者持有独家协议可申请归属变更。

变更流程：提交协议 → 系统记录当前房源状态快照 → 后台审核 → 执行前二次校验当前状态 → 通过后转移归属。双方都有独家协议：管理员人工裁判。

## 4.3 归属变更的状态限制

独家委托的效力高于一切**展示状态**，但不高于**交易状态**。

| **房源状态** | **是否允许归属变更** | **说明** |
|---|---|---|
| 在售 | ✔ | 正常流程。但如果存在待确认的成交记录，阻止归属变更并通知申请人等成交处理完再申请。 |
| 暂停挂牌 | ✔ | 独家委托不因暂停展示而失效 |
| 待确认 | ✔ | 正常流程 |
| 即将上市 | ✔ | 正常流程 |
| 已下架 | ✔ | 正常流程 |
| 锁定（经纪人离职） | ✔ | 独家委托优先级高于门店内移交 |
| 定金已付 | ✖ | 交易状态锁定，买方已介入 |
| 成交进行中 | ✖ | 交易状态锁定，过户流程中 |
| 已售 | ✖ | 交易状态锁定，交易已完成 |
| 撤牌 | ✖ | 房源已终结 |

## 4.3b 锁定房源的归属变更

经纪人离职后房源进入「锁定」状态（详见模块一V8第八节）。锁定房源接受独家委托归属变更申请，独家委托优先级高于门店内移交。

| **场景** | **处理方式** |
|---|---|
| 房源锁定，门店老板尚未移交，C持独家委托申请变更 | 正常受理，审核通过后归属转给C |
| 房源锁定，门店老板已移交给B，C持独家委托申请变更 | 正常受理，审核通过后从B手中转给C。B收到通知。 |

## 4.4 归属变更通知与申诉（App版渠道调整）

**通知内容**：您录入的房源【XX小区 X栋 X单元 XXX】已被持有独家委托的经纪人接管。如有异议请在7天内提交申诉。

**通知方式（App版）**：极光推送 + 微信服务号（如绑定） + 消息中心。

**申诉机制**：后台审核通过后立即执行归属转移。原经纪人7天内可附证据提交申诉，管理员裁判。申诉成功则回滚归属转移，回滚范围如下：

| **操作类型** | **回滚方式** |
|---|---|
| 调价 | 回滚到变更前价格 |
| 状态变更 | 回滚到变更前状态 |
| 新审批的带客申请 | 标记为无效，通知相关BA |
| 已完成的带看记录 | 保留不回滚——带看是真实发生的事实 |
| 已公开的身份信息 | 不做回撤——已经互相知道了 |
| 奖金设定 | 回滚到变更前值 |

回滚操作记入audit_log。

## 4.4b 归属变更时的关联数据处理

### 奖金重置

归属变更后，合作奖金重置为0。新归属人自行设定新的奖金金额。奖金重置记入bonus_history。

系统通知以下相关方奖金已重置：收藏该房源的经纪人、待审批的带客申请人、已通过的带客申请人、已完成带看的Buyer's Agent。

### 带客申请处理

| **申请状态** | **处理方式** |
|---|---|
| 待审批 | 转移给新Listing Agent。待审批列表中标注「归属变更前申请，原Listing Agent: XXX」 |
| 已通过（未完成带看） | 保持有效。通知Buyer's Agent：房源Listing Agent已变更为XXX，您的带客申请仍然有效。**7天有效期从转移时刻重新计算。** |
| 已完成带看 | 不动。带看记录保留完整历史。 |

### 开放看房日处理

归属变更后，如有未来的开放看房日，系统自动取消并通知所有已收到开放日通知的经纪人。新归属人需重新设定开放看房日。取消操作记入audit_log。

### 个人备注处理

归属变更后，原经纪人的个人备注**不迁移**给新归属人。原经纪人保留该房源的个人备注记录（只读，不可编辑）。新归属人从零填写自己的个人备注。联卖备注（公开备注）随房源转移，新归属人可编辑。

## 4.5 经纪人离职时的房源处理

经纪人离开门店或离职时，其名下房源的锁定与移交机制详见模块一V8第八节。门店老板可通过管理页将锁定房源重新分配给其他经纪人。移交操作等同于归属变更，记入audit_log。

# 五、房源状态流转（业务不变）

| **状态** | **含义** | **触发方式** | **共享库展示** |
|---|---|---|---|
| 即将上市 | 已签独家委托但未准备好看房 | 经纪人录入时选择，必须上传独家委托协议 | 展示，蓝色标签，不可申请带客 |
| 在售 | 正常展示，可被申请带客 | 经纪人手动切换或即将上市到期自动转换 | 共享库可见，可申请带客 |
| 定金已付 | 买家已付定金，双方仍可能反悔 | 经纪人手动标记，必须上传定金凭证 | 展示，橙色标签，仍可申请带客（backup） |
| 成交进行中 | 正在走过户流程 | 经纪人手动标记 | 展示，灰色标签，不再接受带客 |
| 已售 | 通过本平台成交确认流程完成 | 只能通过交易留痕流程触发 | 展示成交价、成交时间 |
| 撤牌 | 其他渠道成交/房东不卖/其他原因 | 仅从「在售」或「待确认」状态手动标记 | 不展示 |
| 暂停挂牌 | 经纪人主动暂停展示 | 经纪人手动标记，需选原因 | 不展示，紫色标签（仅自己管理页可见） |
| 待确认 | 7天未更新（仅「在售」触发） | 系统自动 | 仍展示，黄色标签 |
| 已下架 | 14天未更新/委托到期/封禁 | 系统自动（仅从「待确认」触发） | 不展示 |
| 锁定 | 经纪人离职，房源待移交 | 门店老板移除经纪人或后台标记离职 | 展示，灰色标签「经纪人已离职，待移交」，不可申请带客 |

## 5.1 状态流转规则

**核心原则：交易状态链是严格递进关系，不可跳步。回退是逆向递减（已售不可回退，成交进行中→在售，定金已付→在售）。此原则对所有操作人（LA、BA、系统、后台）一视同仁，无豁免。两条递进路径：**
- **常规路径：** 在售→定金已付→成交进行中→已售
- **无定金路径：** 在售→成交进行中（上传购房合同凭证）→已售

即将上市 → 在售：经纪人手动切换，或录入时设定的预计上市日期到达后系统自动转换。

在售 → 定金已付：经纪人手动标记。需填写定金金额（仅自己和后台可见）。**必须上传定金凭证（转账截图或收据照片），无凭证不可标记。虚假标记定金属于严重违规。**

定金已付 → 在售：买方反悔或交易取消，经纪人手动恢复。需选原因。30天内标记/回退合计超过2次系统自动标记异常供后台审查。

定金已付 → 成交进行中：过户流程启动，经纪人手动标记。

**在售 → 成交进行中（无定金交易）**：部分交易无独立定金环节。LA可标记"本交易无定金，直接签约"，**必须上传购房合同照片作为凭证**，房源状态从在售直接跳到成交进行中。

成交进行中 → 已售：只能通过交易留痕流程的「成交确认」节点触发。

成交进行中 → 在售：交易取消，经纪人手动标记回退。需选原因。DOM恢复继续计算。

在售 → 暂停挂牌：经纪人手动标记。需选原因。**如有未来的开放看房日，系统自动取消并通知相关经纪人。存在待确认的成交记录时，不可暂停挂牌。**

暂停挂牌 → 在售：经纪人手动恢复。DOM恢复继续计算。

在售/待确认 → 撤牌：经纪人手动标记，需选原因。**撤牌只能从「在售」或「待确认」状态触发。**

| **当前状态** | **能否直接撤牌** | **路径** |
|---|---|---|
| 在售 | ✔ | 直接撤牌 |
| 待确认 | ✔ | 直接撤牌 |
| 定金已付 | ✖ | 先回退到在售 → 再撤牌 |
| 成交进行中 | ✖ | 先回退到在售 → 再撤牌 |
| 暂停挂牌 | ✖ | 先恢复到在售 → 再撤牌 |
| 即将上市 | ✖ | 先转在售或等到期下架 |
| 有待确认成交记录 | ✖ | 先驳回成交确认 → 再撤牌 |

「已售」状态经纪人不能手动标记，只能通过交易留痕流程触发。

## 5.2 「即将上市」状态详细规则

| **规则** | **说明** |
|---|---|
| 强制独家委托 | 必须上传独家委托协议，否则无法选择此状态 |
| 预计上市日期 | 必填，到期自动转为「在售」。最长不超过30天。 |
| DOM不计算 | Days on Market从转为「在售」时才开始计算 |
| 不可申请带客 | 其他经纪人可以看到房源信息，但无法发起带客申请 |
| 可收藏 | 其他经纪人可以收藏，转为「在售」时收到通知 |
| 到期未转在售 | 到期后系统发通知提醒经纪人操作。如不转在售，立即下架。下架后如需重新上架，只能选「在售」状态，不再提供「即将上市」选项。 |

> *同一套房源每个挂牌周期只能使用一次「即将上市」状态。重新上架开启新周期时，即将上市额度重置。*

## 5.3 「暂停挂牌」状态详细规则

| **规则** | **说明** |
|---|---|
| 触发方式 | 经纪人从「在售」状态手动切换，需选原因 |
| 共享库展示 | 不展示。暂停期间房源从共享库消失，仅经纪人自己的房源管理页可见 |
| DOM暂停 | 暂停挂牌期间DOM停止计算，恢复在售后继续计算 |
| 最长暂停时间 | 60天。超过60天系统自动将房源转为「撤牌」状态 |
| 自动撤牌时带客申请 | 暂停超时自动转撤牌时，暂停期间保持有效的带客申请进入冻结状态（不关闭）。恢复上架后自动解冻并通知相关BA。 |
| 未完成的带客 | 暂停前已通过的带客申请保持有效，相关BA收到房源暂停通知 |
| 开放看房日 | 暂停时如有未来的开放看房日，系统自动取消并通知已收到开放日通知的经纪人 |
| 恢复 | 经纪人手动切回「在售」，房源重新出现在共享库 |
| 恢复上架委托检查 | 恢复上架时系统检查委托状态。如果撤牌期间委托已到期，需上传新委托才能恢复上架。 |
| 归属变更不受限 | 暂停挂牌属于展示状态，不影响归属变更 |

## 5.4 「待确认」和自动下架的作用范围

| **规则** | **说明** |
|---|---|
| 触发范围 | 仅「在售」状态的房源。7天未更新标记为「待确认」，14天未更新自动下架 |
| 不触发的状态 | 即将上市、定金已付、成交进行中、暂停挂牌 |
| 委托到期下架 | 不受此限制，任何状态的房源委托到期都会下架。但「成交进行中」的房源委托到期只提醒续委托不自动下架。 |
| 「更新」的定义 | ①内容更新——修改房源信息；②状态确认——系统弹出"该房源是否仍在售？"，经纪人点击"确认继续上架"即视为更新。 |

> *待确认→已下架时的带客申请处理：自动下架时（从待确认14天未更新触发），已通过但未完成带看的带客申请保持有效（不冻结、不关闭），通知BA。LA恢复上架后可继续。*

## 5.5 DOM计算规则

| **状态** | **DOM是否计算** |
|---|---|
| 即将上市 | 不计算 |
| 在售 | 正常计算 |
| 定金已付 | 正常计算 |
| 成交进行中 | 暂停计算 |
| 暂停挂牌 | 暂停计算 |
| 已售 | 停止计算，展示最终DOM |
| 撤牌/已下架 | 停止计算 |
| 锁定 | 暂停计算 |

> *数据结构：houses集合字段——dom_paused_at（暂停时间）、dom_accumulated（暂停前已累计的天数）、current_listing_cycle（当前挂牌周期序号）、listing_cycles[]（每个周期起止信息）。DOM = dom_accumulated +（当前时间 - 最后一次恢复计算的时间）。采用美国MLS的Active DOM方式。*

# 七、照片上传机制（V11 App版全新章节）

## 7.1 照片类型与上传要求

| **类型** | **必填数量** | **压缩策略** | **EXIF处理** | **防作弊** |
|---|---|---|---|---|
| 实拍照片 | ≥3张 | 最长边1920px，质量80%，JPG | 保留拍摄时间 | 可配置"仅相机"模式 |

| 定金凭证 | 1张或多张 | 最长边2400px，质量90% | 保留完整EXIF | 原图hash+水印校验 |
| 购房合同（无定金路径） | 1张或多张 | 最长边2400px，质量90% | 保留完整EXIF | 原图hash后台记录 |

## 7.2 Flutter技术实现

### 7.2.1 图片选择与压缩

```dart
// 伪代码
final picker = ImagePicker();
final List<XFile> images = await picker.pickMultiImage(
  maxWidth: 1920,
  maxHeight: 1920,
  imageQuality: 80,
);

// 二次压缩保障（image_picker的压缩不稳定）
for (final img in images) {
  final compressed = await FlutterImageCompress.compressWithFile(
    img.path,
    minWidth: 1920,
    minHeight: 1920,
    quality: 80,
    keepExif: true,  // 保留EXIF
  );
  // 上传到 COS
  await uploadToServer(compressed);
}
```

### 7.2.2 上传机制

- **Dio + MultipartFile**：HTTP POST 到后端，后端转发到腾讯云COS（服务端签名上传）
- **进度监听**：`onSendProgress` 回调，UI展示每张图的进度条
- **并发上传**：最多3张并发，其余排队
- **失败重试**：单张失败最多重试2次，3次失败后标记失败状态，不阻塞其他图片
- **上传完成返回URL**：后端返回COS URL，前端更新UI

### 7.2.3 批量上传UI

```
┌─────────────────────────────────────┐
│ 实拍照片（至少3张）                 │
├─────────────────────────────────────┤
│ ┌────┐ ┌────┐ ┌────┐ ┌────┐       │
│ │ 📷 │ │IMG1│ │IMG2│ │IMG3│       │
│ │ +  │ │ ✓  │ │ 85%│ │ ✗  │       │ ← 状态图标
│ │    │ │    │ │上传│ │重试│       │
│ └────┘ └────┘ └────┘ └────┘       │
└─────────────────────────────────────┘
```

- ✓ 上传成功
- 85% 进度条
- ✗ 失败（点击重试）
- 长按：删除

## 7.3 防作弊机制

### 7.3.1 EXIF校验

上传时后端校验EXIF：
- 拍摄时间应在上传时间前30天内（过旧的照片可能是盗用）
- 如拍摄时间缺失或异常，标记"来源可疑"由后台人工审核

### 7.3.2 图片hash去重

后端为每张图片计算 pHash（感知哈希），记录到 house_photos 集合：
- 同一经纪人上传相同或近似的图片到不同房源时触发告警（可能盗图）
- 不同经纪人上传相同图片时标记"疑似盗图"由后台审核

### 7.3.3 带看凭证"仅相机"模式

带看现场照片**必须通过相机实时拍摄**，禁用相册选择。实现方式：`ImagePicker.pickImage(source: ImageSource.camera)`，只暴露相机入口。详见模块四§5.2。

### 7.3.4 定金凭证额外校验

定金凭证上传后：
1. 原图hash存档
2. 后台定期巡检新上传的定金凭证
3. 异常情况（多张相同凭证、明显PS痕迹）触发审查
4. 发现虚假凭证：回滚状态+严重违规处罚

## 7.4 照片查看器

查看房源详情时的照片浏览：
- 插件：`photo_view`
- 支持手势缩放（双击/双指）
- 多图滑动浏览：`PageView` 组件
- 全屏模式：点击图片进入全屏，再次点击退出
- 保存到相册：长按菜单（仅限本人房源的照片，防盗图）

# 八、离线草稿机制（V11 App版新增）

## 8.1 设计目标

经纪人录入房源时可能遇到弱网或临时切出App的情况。支持本地暂存+恢复，避免数据丢失。

## 8.2 实现方式

**存储**：使用 Hive 本地NoSQL存储，box名 `house_drafts`。

**数据结构**：

```dart
class HouseDraft {
  String draftId;           // 草稿ID
  DateTime createdAt;
  DateTime updatedAt;
  Map<String, dynamic> formData;  // 表单所有字段
  List<String> localPhotoPaths;   // 本地照片路径（未上传）
  List<String> uploadedPhotoUrls; // 已上传的照片URL
  String status;  // draft / uploading / failed
}
```

## 8.3 自动保存

- 表单字段变更时防抖500ms自动保存到Hive
- 照片选择后立即保存本地路径
- App崩溃或强制关闭后重新打开可恢复到最后保存状态

## 8.4 草稿列表与恢复

「我的房源」顶部展示"未完成的草稿 X条"入口：
- 点击进入草稿列表
- 每个草稿展示：最后编辑时间、小区名、已填写字段数、已上传照片数
- 点击草稿：恢复到录入页继续编辑
- 长按：删除草稿

## 8.5 提交策略

| **场景** | **行为** |
|---|---|
| 表单完整 + 联网 | 点击"提交"直接提交到后端 |
| 表单完整 + 弱网/离线 | 点击"提交"后本地标记 status=uploading，联网后自动尝试提交 |
| 表单不完整 | 仅暂存为草稿，不提交 |
| 提交失败 | status=failed，展示失败原因，用户可重试 |
| 提交成功 | 删除本地草稿+照片缓存 |

## 8.6 约束

- 草稿最多保留30条，超出按最老顺序自动清理
- 草稿保留时间最长30天，超时提示用户清理
- 离线状态下可编辑草稿但不能查重（需联网确认小区+房号是否已存在）

# 九、照片与信息审核机制（业务不变）

## 9.1 照片基本要求

至少3张实拍照片。首张照片应为房屋外观或客厅全景。照片必须是该房源的实拍，不允许使用其他房源照片。不允许在照片上添加文字水印、名片、二维码等遮挡物。

## 9.2 审核方式

种子期：后台运营人员定期巡检，发现不合规的照片或信息，下架房源并通知经纪人完善。后期迭代：接入图片审核API（阿里云内容安全/腾讯云T-Sec）。

## 9.3 处罚机制

首次不合规：下架房源 + 通知完善，完善后可重新上架。多次不合规：按模块五处罚体系处理。

# 十、小区库（业务不变+App交互增强）

## 10.1 作用

小区库是平台基础数据。经纪人录房源时从库中选择小区，详细信息自动带出。同小区所有房源共享一份信息。

## 10.2 字段结构（后台维护）

基础信息：标准名、别名（多个）、所属区域、地址、建成年代、建筑类型、交易权属、开发企业、总户数、楼栋数。生活信息：供暖类型、用水类型、用电类型、燃气费用。居住环境：容积率、绿化率、人车分流、是否封闭。车位信息：车位配比、停车费。

## 10.3 权限

| 查看小区详情 | ✔ | ✔ | ✔ |

## 10.4 搜索与合并逻辑

**搜索（App版交互）**：
- TextField + 防抖300ms触发搜索
- 同时匹配标准名和别名
- 结果格式「标准名（别名）」
- 支持拼音首字母模糊匹配
- 本地缓存最近10次搜索结果，快速重用

**合并**：A合并入B时，A下房源归B，A名称添加为B别名，关注A的经纪人自动转为关注B，A从库中删除。操作记入audit_log。

## 10.5 App地图展示（V11新增）

房源详情页展示小区地图：
- 高德地图Flutter SDK（`amap_flutter_map`）
- 使用小区的经纬度坐标（后台维护）
- 仅展示小区位置，不展示具体楼栋（保护隐私）
- 支持点击跳转高德地图App导航

# 十二、并发控制技术方案（业务不变）

| **并发场景** | **解决方案** | **技术手段** |
|---|---|---|
| 两个经纪人同时重新上架同一套已售房源 | 乐观锁——条件更新检查当前status | `findOneAndUpdate({status: "已售"}, {$set: ...})`，第二个失败提示"已被他人上架" |
| 定金标记与归属变更同时执行 | 二次校验+条件更新 | 归属变更执行时检查`{status: {$nin: ["定金已付","成交进行中","已售"]}}` |
| 归属变更的连锁操作期间有新操作 | MongoDB多文档事务 | 归属变更全部连锁操作在一个事务中完成，保证原子性 |
| 7天超时自动生效与LA手动驳回同一毫秒 | 乐观锁——条件更新检查status | 定时任务和手动操作都检查`{status: "待确认"}`，只有匹配才执行 |
| 多人同时收藏同一房源 | 原子操作+每日校准 | `$inc`原子操作 |

## 13.4 上传架构

```
App选择图片
  ↓
本地压缩（image_compress）
  ↓
GET /api/upload/signature → 后端返回COS直传签名
  ↓
Dio直接上传到腾讯云COS（不过后端，节省带宽）
  ↓
上传成功 → POST /api/houses/:id/photos 告知后端新照片URL
  ↓
后端写入 house_photos 集合
```

**优势**：
- 照片直传COS，不过业务后端，减轻服务器带宽压力
- COS签名有时效（5分钟），签名防篡改
- 后端只记录最终URL，不处理二进制

## 13.5 异常与兜底

| **场景** | **处理** |
|---|---|
| 上传过程中App被杀 | 本地照片记录保留在Hive草稿，重开App自动提示"有未完成的上传，是否继续" |
| 网络抖动 | Dio内置重试机制，最多3次，失败后标记失败由用户手动重试 |
| COS签名过期 | 自动重新请求签名后重试 |
| 图片过大（>10MB） | 压缩失败时提示用户"图片过大，请选择较小的图片" |
| 图片损坏 | FlutterImageCompress返回null时提示重新选择 |
| 权限被拒 | 引导用户跳转系统设置 |
