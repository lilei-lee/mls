# 一、模块概述

MLS App通过**三层推送架构**保证业务通知的可达性：

1. **第一层（核心通道）**：极光推送JPush聚合华为/小米/OPPO/VIVO/荣耀/魅族厂商直连通道 + FCM（海外备用）+ APNs（iOS预留）。覆盖App在后台或被杀死状态下的离线推送。
2. **第二层（辅助通道）**：微信服务号模板消息。用于高优先级事件的双通道冗余，以及用户卸载App或权限关闭时的兜底。需用户已绑定微信UnionID。
3. **第三层（兜底）**：App内消息中心。所有通知无论是否离线推送成功都入库，用户打开App时通过拉取和角标展示保证看到。

> *门店老板以经纪人身份参与业务时，接收与普通经纪人完全相同的业务通知。门店管理相关通知（如名下经纪人变动）为门店老板专属。*

# 二、推送通道架构

## 2.1 通道能力对比

| **通道** | **到达率** | **离线送达** | **触达前提** | **字符限制** | **点击跳转** |
|---|---|---|---|---|---|
| 极光推送聚合（华米OV+FCM） | 95%+（厂商通道）/ 60-70%（自建通道） | ✔ | App已安装+通知权限开启 | 标题32字+内容128字 | 支持深度链接 |
| 微信服务号模板消息 | 95%+（用户关注且活跃） | ✔ | 用户关注服务号+UnionID已绑定 | 模板固定格式 | 支持跳转小程序或H5 |
| App内消息中心 | 100%（兜底） | ✖（需打开App） | 无 | 无限制 | 支持App内任意路由 |

## 2.2 三层推送流程

```
后端业务事件触发
  ↓
推送调度器（Push Scheduler）
  ↓
1. 生成唯一 message_id（用于去重）
  ↓
2. 写入 notifications 集合（App内消息中心数据）
  ↓
3. 根据事件优先级与用户偏好决定渠道组合：
  ├─ 高优先级（带客申请/成交确认/争议） 
  │  → 极光推送 + 服务号（如绑定） + 消息中心
  ├─ 中优先级（房源变动/奖金提醒/反馈请求）
  │  → 极光推送 + 消息中心
  └─ 低优先级（系统提示/收藏变动）
     → 消息中心（应用内红点）
  ↓
4. 调用极光推送 REST API
  ├─ 极光根据设备厂商分发到对应通道
  ├─ 推送结果回调 → 写入 push_log
  └─ 失败 → 记录原因，不重试（兜底由消息中心承担）
  ↓
5. 如触发服务号：调用微信模板消息 API
  ↓
6. App收到推送
  ├─ 检查 message_id 是否已在本地显示过
  ├─ 未显示 → 展示通知 + 写入本地已显示池
  └─ 已显示 → 丢弃（去重）
```

## 2.3 极光推送与厂商通道

极光推送JPush在国内Android生态承担聚合角色，自动根据手机厂商将消息路由到对应的官方通道，以获得最高到达率和最低被杀进程限制：

| **厂商** | **直连通道** | **国内主流机型覆盖** |
|---|---|---|
| 华为 | HMS Push | 华为全系+荣耀早期机型 |
| 小米 | MiPush | 小米/红米全系 |
| OPPO | OPPO Push | OPPO/一加/真我 |
| VIVO | VIVO Push | VIVO/iQOO |
| 荣耀 | Honor Push | 2022年后独立荣耀机型 |
| 魅族 | Flyme Push | 魅族全系 |
| 其他（三星/锤子/索尼等） | FCM / 极光自建长连接 | 低于整体5%，可接受 |
| iOS（未来） | APNs | - |

**厂商通道审核要求**：各厂商推送平台对推送内容有审核要求，营销类消息限制严格，业务通知（系统通知）相对宽松。所有模板需提前在各厂商后台报备。

# 三、通知渠道选择原则

| **紧急程度** | **通知渠道** | **典型场景** |
|---|---|---|
| 高（需立即处理） | 极光推送 + 微信服务号（如绑定） + App内消息中心 | 带客申请待审批、成交确认待确认、争议举报通知、被处罚通知 |
| 中（当天了解即可） | 极光推送 + App内消息中心 | 房源调价、带看反馈请求、奖金结算提醒、关注小区新房源 |
| 低（知道就行） | 仅App内消息中心 | 收藏房源待确认、即将上市转在售、功能限制到期提醒 |

> *V10说明：微信服务号作为辅助通道，不强制绑定。用户不绑定微信时，高优先级事件退化为"极光推送+消息中心"双通道；如果App推送权限也被关闭，则完全依赖消息中心，会有延迟但不丢失。*

# 五、Android推送技术规范（V10新增）

## 5.1 Notification Channel（Android 8+必须）

Android 8.0（API 26）起要求所有通知必须归属一个Channel，用户可按Channel分别控制（关闭/免打扰/横幅/响铃）。本App定义4个Channel：

| **Channel ID** | **Channel名** | **重要性** | **用途** | **默认行为** |
|---|---|---|---|---|
| `channel_transaction` | 交易通知 | HIGH（IMPORTANCE_HIGH） | 成交确认、奖金结算、争议举报、处罚通知 | 横幅+响铃+震动，锁屏显示 |
| `channel_showing` | 带客通知 | HIGH | 带客申请、审批结果、带看确认、反馈请求 | 横幅+响铃+震动 |
| `channel_system` | 系统通知 | DEFAULT | 账号安全、审核结果、版本更新、设备登录 | 静默横幅，锁屏显示 |
| `channel_marketing` | 房源动态 | LOW | 收藏房源变动、关注小区新房源、奖金调整 | 仅状态栏角标，不横幅不响铃 |

**实现**：App首次启动时通过 `flutter_local_notifications` 注册4个Channel。用户可在系统设置中按Channel关闭，App不可覆盖。

## 5.2 POST_NOTIFICATIONS权限（Android 13+）

Android 13（API 33）起推送通知需要运行时权限 `POST_NOTIFICATIONS`：

- **请求时机**：首次登录成功后，进入工作台前的引导弹窗
- **文案**："为了及时接收带客申请、成交确认等关键业务通知，请允许发送通知"
- **用户拒绝处理**：
  - 工作台顶部展示"通知已关闭，可能错过重要业务消息 · 去开启"提示条
  - 所有推送事件正常写入 App 内消息中心
  - 关键操作页（如有待审批申请时进入工作台）再次引导开启

## 5.3 厂商通道对接准备

极光推送承担了大部分厂商对接工作，但以下准备工作必须完成：

| **厂商** | **准备工作** | **预计周期** |
|---|---|---|
| 华为HMS | 华为开发者账号+应用签名SHA256+华为推送服务申请 | 1-3天 |
| 小米MiPush | 小米开发者账号+应用包名+推送AppKey | 1天 |
| OPPO Push | OPPO开发者账号+应用签名+推送权限申请 | 3-5天 |
| VIVO Push | VIVO开发者账号+应用包名+推送权限申请 | 3-5天 |
| 荣耀Push | 荣耀开发者账号（独立）+应用签名 | 3-5天 |
| 魅族Flyme | 魅族开发者账号+推送AppKey | 1-2天 |
| FCM（Google） | Firebase项目+google-services.json | 即时 |

**成本**：上述开发者账号大多免费，推送服务基础额度免费。

## 5.4 厂商审核与文案规范

各厂商对推送文案有审核要求，违规推送会被降级（从厂商通道退化到自建通道，到达率骤降）。

| **规范** | **说明** |
|---|---|
| 禁止敏感词 | 不使用"红包"、"礼品"、"福利"、"赚钱"、"中奖"等营销词汇 |
| 业务类 vs 营销类 | 业务通知标记为"系统消息/服务通知"，审核宽松。营销类须标识"营销" |
| 模板预报备 | 所有通知模板应在极光后台提前提交厂商审核（极光支持聚合报备） |
| 夜间推送限制 | 22:00-次日8:00避免非紧急推送 |
| 频率限制 | 同一用户单日推送不超过3次营销类，业务类不限 |

**原则**：本App业务通知占绝对主体（90%+），营销类仅限"关注小区新房源"等，应按业务类申报。

## 5.5 推送数据载荷

为降低厂商字符限制影响和减少敏感数据暴露，推送载荷采用最小化设计：

```json
{
  "notification": {
    "title": "新的带客申请",
    "body": "房源【北方明珠 2室1厅】有新带客申请，请审批"
  },
  "data": {
    "message_id": "msg_abc123",
    "event_type": "showing_request_new",
    "target_id": "req_xyz789",
    "deep_link": "/showing-requests/req_xyz789"
  }
}
```

App收到后用 data 字段的 `deep_link` 和 `target_id` 拉取最新详情展示。**详情不直接放在推送中**，避免数据过时（例如申请已被撤回而推送仍显示"待审批"）。

## 5.6 推送去重机制

同一业务事件可能通过多个通道同时到达（如极光推送+服务号+App内消息中心），App必须去重：

```dart
// 伪代码
onReceivePush(RemoteMessage message) {
  String messageId = message.data['message_id'];
  if (hiveBox.get('shown_messages').contains(messageId)) {
    return; // 已显示过，丢弃
  }
  showNotification(message);
  hiveBox.get('shown_messages').add(messageId);
  // 清理30天前的ID，防止无限增长
}
```

## 5.7 冷启动消息同步

极光推送有一定的失败率（厂商通道限制、长连接断开、系统内存回收等）。App冷启动时主动拉取补偿：

```
App启动 → 登录态有效
  ↓
GET /api/notifications/pending?since=last_active_at
  ↓
后端返回用户最后活跃后未读的所有通知
  ↓
App对比本地已显示池，补展示遗漏的通知（仅写入消息中心，不重弹通知）
  ↓
更新 last_active_at
```

## 5.8 徽标/角标（Badge）

Android厂商对徽标的支持差异大：

| **厂商** | **徽标支持** | **实现方式** |
|---|---|---|
| 华为 | ✔ | ShortcutBadger + HMS Push带 badgeCount |
| 小米 | ✔ | MiPush notifyType + 通知计数 |
| VIVO | ✔ | VIVO Push聚合 |
| OPPO | ⚠ | 受限，部分机型不支持 |
| 原生Android | ✖ | 仅Android 8+的 Notification Badge，不显示数字 |

**策略**：
- 厂商支持的情况下通过极光聚合API设置徽标数
- 底部Tab"消息"Tab上展示红点+未读数（Flutter内部实现，不依赖系统徽标）
- App图标Badge作为辅助展示，不作为核心依赖

| 模块六（Web管理后台） | 后台手动操作通知、代完成成交确认通知 | 通过上述模块间接触发 |

共计约70种通知类型 + 2种预留（订阅搜索匹配）。

# 十二、小程序→App迁移说明

本模块是决策汇总中小程序→App迁移变化最大的模块。核心替换：

| **小程序原设计** | **App版替换** |
|---|---|
| 微信服务号模板消息（主通道） | 极光推送JPush聚合厂商通道（主通道） |
| 小程序内消息（辅助） | App内消息中心（兜底） |
| UnionID打通服务号推送 | UnionID**可选**打通服务号（作为第二层辅助通道） |
| 模板消息审核流程 | 各厂商推送模板审核（极光后台聚合提交） |
| 无Notification Channel | Android Notification Channel分4类 |
| 无运行时权限 | Android 13+ POST_NOTIFICATIONS运行时申请 |
| 推送数据明文 | 推送载荷仅 message_id + deep_link，详情App内拉取 |

**后端通知逻辑保留 95% 不变**：业务触发、通知对象、文案、频率控制等完全一致。只需替换推送调用层（从微信模板消息API换成极光REST API+保留服务号作为可选通道）。

**双端并行过渡**（可选）：如小程序和App并行运行一段时间，同一用户（同一UnionID）两端均可收到服务号通知，App端额外收到极光推送。去重机制保证不重复展示。
